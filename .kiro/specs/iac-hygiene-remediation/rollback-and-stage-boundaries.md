# 切り戻し可能性と段階境界

本書は `iac-hygiene-remediation` の是正を安全に停止・再開できるようにするための運用参照文書である。対象は `my-home-network` / `gitops-apps` / `portfolio` の3リポジトリと、Proxmox 上のゲスト、k3s クラスタ、エッジホスト (VPS) の実機である。

**適用対象外**: Proxmox VM 105 (nextcloud) は本 spec の管理対象外であり、本書のいずれの記述もこのゲストには適用されない。切り戻し・保全・停止条件の検討対象からも除外する。

段階の区切りは `tasks.md` 冒頭が定めるとおり、段階 0 → 0.5 → 1 → 2 → 3 → 4 である (`.kiro/specs/iac-hygiene-remediation/tasks.md` 3-21 行目)。各段階の対象タスクと完了条件は `design.md` の Migration Strategy 節 (同ファイル 1817-1908 行目) に定義済みであり、本書はそれを土台に、実施済みの内容で確認した事実を反映して更新する。

## 1. 現在の到達段階

`tasks.md` の全タスクがチェック済みである。段階 0 から段階 4 に属する全タスクについて、実機・クラスタへの適用と変更履歴への記録が完了している。

段階 3 の完了条件は「履歴走査の検出がゼロ」を含む (design.md Migration Strategy 表)。`my-home-network` の全履歴に対する走査で検出ゼロを確認済みであり、段階 3 は完了している。ただし段階 4 (タスク 22: ワークロードの品質規約) の内容は、段階 3 の完了条件が確定するより前に適用された。design.md の flowchart が前提とする `S3 → V3 → S4` の順序からの逸脱であり、8 節に記録する。

## 2. 切り戻しの対象範囲: マニフェストの復元とデータの復元

### 2.1 マニフェストの復元

マニフェストの復元は `git revert` (または対象コミット以降の取り消し) によって行う。前提は、リポジトリごと・変更単位ごとに分離してコミットされていること (要件 12.12)、および高影響な変更が他の変更と分けて適用されていること (要件 12.13) である。

**リポジトリ別の現状**:

| リポジトリ | 状態 | マニフェスト復元の実施可否 |
|---|---|---|
| `gitops-apps` | 作業ツリーはクリーン。タスク単位で個別コミットされている | 個別コミット単位で `git revert` が可能。高影響カテゴリ (リソース制限の導入、静的 PV への切替等) も他の変更と分離したコミットとして識別できる |
| `portfolio` | 作業ツリーはクリーン。タスク単位で個別コミットされている | 同上 |
| `my-home-network` | 作業ツリーはクリーン。段階 0 から段階 4 の変更が 20 コミットへ分離されている。高影響カテゴリ (クラスタトークンのローテーション、エッジホストの境界防御、Gitea DB 移設、Terraform ゲスト定義、認証基盤の新設、ディスク割当のロール化、バックアップ API トークンの権限最小化) はいずれも単独コミットとして識別できる | 個別コミット単位で `git revert` が可能 |

3 リポジトリすべてについて、要件 12.12 (リポジトリごとに独立してコミット可能な単位への分割) および 12.13 (高影響な変更を他の変更と分けて適用する) が変更履歴上で確認できる。以下は `my-home-network` において適用されている分離粒度であり、design.md の「承認ゲート」表および高影響カテゴリの定義 (要件 12.13: 認証情報のローテーション、git 履歴の書き換え、Terraform の差分抑止解除、ワークロードへのリソース制限導入、カスタムリソース定義の削除) に対応する。

| 分離すべき単位 | 対応するタスク |
|---|---|
| クラスタトークンのローテーションと配布経路変更 | 21.1 |
| 平文コミットされた資格情報のローテーション | 21.2 |
| 公開リポジトリの履歴書き換え | 21.3 (通常の commit ではなく履歴書き換え操作として実施) |
| Terraform の差分抑止解除 + 領域返却設定 | 21.4, 21.9 |
| 証明書発行系 / 論理レプリケーション基盤の operator 更新 | 21.5, 21.6 |
| NAS 共有の権限是正 | 21.7 |
| クラスタ上の古い鍵の除去 | 21.8 |
| Proxmox ゲストの整理・除去 (CT 100 除去、MinIO zvol 削除、Gitea DB 移行) | 28.1-28.6 |
| エッジロールの実適用・ファイアウォール有効化 | 3.2, 12.1-12.7 |
| Workers への配信移設 | 24.1-24.8 |

`gitops-apps` は既にこの粒度に近い分離がコミット履歴上で実現している。例 (subject 行で識別、hash には依存しない):
- `feat(resources): ArgoCD管理下の全ワークロードにリソース要求/上限を設定する` — ワークロードへのリソース制限導入 (高影響カテゴリ) が単独コミットになっている
- `feat(garage): metadata_dir/data_dir を分離した静的 PV へ切り替える` / `feat(garage): metadata/data 分離用の静的 PV/PVC を追加` — ストレージ構成変更が単独コミット群になっている
- `abf8e08 feat(applicationset): apps/base を生成対象から除外し不要な StorageClass を削除` (StorageClass 定義の削除、段階 4 の承認ゲート対象) が単独コミットになっている

### 2.2 データの復元

データの復元は対象ごとに経路が異なる。「クラスタ内の永続データの復旧」は design.md の Out of Boundary が明示するとおり本 spec の対象外であり、クラスタ全体の再構築を許容範囲とする前提がある。したがって以下は、この前提の外側にある対象 (Proxmox ゲスト単位、ホストファイルシステム、リポジトリ履歴) を優先し、クラスタ内データについては実際に確認できた保護経路を記録するに留める。

## 4. 段階境界の停止条件

段階の完了時点で止めた場合の整合状態と未是正の範囲は、design.md Migration Strategy の「段階境界の停止条件」表 (1887-1901 行目) のとおりであり、本 spec の実施結果はこれと整合している。同表を要約する。

| 段階境界 | 停止時点で整合している内容 | 未是正のまま残る範囲 |
|---|---|---|
| 0 完了 | 構成管理が実行可能、公開配信が回復済み | エッジホストの実機と定義の乖離、mailu/xrayvpn/クラスタ孤児は稼働時のまま |
| 0.5 完了 | 全ホストへ実行環境に依らず到達可能、乖離が記録済み、実機の設定退避済み | 記録した乖離の解消そのもの、バックアップは未機能、ゲスト定義取り込みの判断は未確定 |
| 1 完了 | 削除完了・Git とクラスタが対応、メール経路が閉じている、バックアップが機能、認証基盤/Dashboard 撤去済み | メール基盤・新認証基盤は未構築、安全でない既定値・冪等性・トークン・履歴・`ignore_changes` は未是正 |
| 2 完了 | ロール再実行で差分なし、静的解析成功、両リポジトリに検証 CI、認証基盤稼働・統合済み | 漏洩トークンと履歴、公開サイトはエッジホスト依存のまま、resources/probe/securityContext 未設定 |
| 3 完了 | 漏洩認証情報が失効、公開サイトがエッジホストから独立、証明書供給が単一機構、ディスク領域返却が反映済み | ワークロードの品質規約、定義方式の統一、StorageClass の除去 |
| 4 完了 | 全要件完了 | — |

**現在の位置づけ**: 段階 4 完了。段階 3 の完了条件 (履歴走査の検出ゼロ) も確定している。ただし段階 4 の内容は段階 3 の完了条件が確定するより前に適用されており、その順序の逸脱は 8 節に記録する。

## 5. 途中停止時の不整合ポイントと再開時の解消優先度

design.md が記録する不整合ポイントのうち、実施結果に照らして再確認できたものと、実施中に新たに判明したものを示す。**本 spec の全タスクが完了しているため、現時点で残存している不整合はない。**以下は途中で停止した場合に備えた記録である。

| 段階 | 不整合が残る境界 | 再開時に最初に解消する対象 |
|---|---|---|
| 3 (解消済み) | クラスタトークンのローテーション (21.1) と履歴書き換え (21.3) の間で止まると、design.md が最も注意すべき不整合として挙げる「履歴上の値は失効済みだが公開面には残る (片側完了)」状態になる | **21.3 の完了を最優先とする。** 記録上の「資格情報が混入した 3 コミット」と差分スキャンの検出件数が食い違う場合、差分スキャンはブロブの導入コミットしか拾わないことに起因する。ブロブのツリー内包含を全コミットに対して集計して所在を確定させたうえで、全履歴走査でゼロを確認する |
| 3 (解消済み) | `my-home-network` の段階 0-4 の変更が単一の未コミット差分に留まる状態。この状態では変更履歴を根拠にした選択的な切り戻しができない | 履歴書き換えの完了後に (書き換えと通常のコミット追加を混在させないため)、2.1 節の分離粒度に従って高影響カテゴリごとにコミットへ分割する。分割の前に、証跡として採取した設定退避ファイルに対してシークレット走査をかけること。リダクション漏れが未追跡ファイル側に残っていることがある |
| 1 (design.md 記載、実施結果と一致) | 既存バックアップ成果物の除去 (15.6) を再構築 (15.4) の完了前に行うと復元可能な成果物ゼロの窓が生じる。mailu のマニフェスト削除とエッジロール実適用の間で止まるとメール待受だけが残る。保護アノテーション付与前に削除を始めると PVC が無防備なまま prune 対象になる。CRD 削除の途中で止まるとコントローラと CRD の一方だけが残る。認証基盤撤去でマニフェスト削除と Ansible ロール削除の間で止まると bind 用認証情報参照タスクが未定義変数で停止する | 該当箇所に立ち戻った場合、この順序 (保全 → 防御 → 削除) を最初から再現する。いずれも実施済みのため、現時点で残存していない |

## 7. 保護経路がない対象・単一障害点

- **Kanidm (SQLite)**: オンボリューム自己バックアップのみで、実質的な保護は VM 152/150/151 いずれかの PBS ゲスト単位スナップショット (日次、2世代) に一本化されている。オフノードの複製機構がなく、これは design.md が明示済みのリスクである。
- **Gitea の MariaDB (移行後)**: PBS ゲスト単位スナップショットの対象から明示的に除外されており、保護経路は新設の論理バックアップ (`mariadb_dump`、日次、14世代) の一系統のみ。実行結果を監視する仕組みは自動化されていない。
- **LXC 113 (旧 mariadb-legacy)**: データ移行後は空のゲストとして残置。ゲスト自体の削除是非は運用者判断待ちのまま未決定。
- **CT 100 除去時のアーカイブ、および `vm-152-disk-0` 削除時のアーカイブ**: いずれも実行者個人のローカルワークステーション上にのみ存在し、PBS・Infisical・リポジトリのいずれの管理下にもない。これらのアーカイブ自体が単一障害点である。
- **`/var/lib/minio` ルートディスク側の孤児データ (`appflowy` 名前空間)**: 削除も定義への取り込みもされておらず、実機に残置されたまま運用者判断待ち。
- **Garage の静的 PV**: ArgoCD の prune・PVC 削除からは保護されるが、`kubectl delete pv` の直接実行や Proxmox 側でのディスク操作には無防備 (design.md および research.md task 28.5 記載のとおり、最終防衛線はホスト/Proxmox operator の運用規律のみに依存する)。
- **`local-path` provisioner が管理する PVC 全般** (home-assistant、mailbox、minecraft-bedrock 等): PVC 削除は実装上 `rm -rf` に直結し、防御は ArgoCD の `Prune=false`/`Delete=false` アノテーションの有無のみに依存する。
- **Infisical / HCP Terraform**: いずれも外部 SaaS であり、値そのもの・state 履歴そのものの保護は本 spec の境界外 (design.md Out of Boundary)。両者へのアカウントアクセス喪失は、シークレット供給および Terraform 管理リソースの追跡可能性を同時に失わせる。
- **`my-home-network` の変更履歴** (2.1 節): 現時点でリポジトリ単位の分離コミットが存在しないため、選択的な `git revert` による切り戻しが機能しない。作業ツリーの喪失 (誤った `git checkout .` 等) がそのまま是正内容の喪失になる。

## 8. 想定外の事象

- **段階 3 完了前の段階 4 適用**: 1 節・4 節に記録したとおり、段階 3 の完了条件 (履歴走査ゼロ) が確定する前に、段階 4 (タスク 22) の内容が適用された。design.md の flowchart は `S3 → V3 → S4` の順を前提としており、この順序が守られていない。タスク 22 の内容はタスク 21.3 に依存しないため実害はないが、段階の完了条件を厳密に運用する場合は記録上の逸脱として扱う。
- **証跡ファイルのリダクション漏れ**: 実機から採取した Secret の一覧を証跡として保存したファイルにおいて、オブジェクトの `data` フィールドは除去されていたが、`kubectl.kubernetes.io/last-applied-configuration` アノテーションに同一の内容が残っていた。追跡対象に加える直前のシークレット走査で検出し、当該アノテーションを除去してから公開リポジトリへ反映した。ファイル名に「redacted」を含むことはリダクションの完了を意味しない。
- **`my-home-network` 側の変更履歴の未分離**: 2.1 節に記録したとおり、要件 12.12/12.13 が求める分離が `my-home-network` について変更履歴上でまだ確認できない。これは 23.2 着手前提としていた「両リポジトリの commit を参照して確認する」という進め方に対する制約であり、`gitops-apps` 側のみで確認を代替した。
- **ルートディスク上の孤児データの発見**: タスク 6.3 の実施過程で、`zfs-pool/vm-152-disk-0` 削除に関連しない、ルートディスク側に残る孤児データ (`appflowy` 名前空間) が発見されている。本タスクのスコープにも先行タスクのスコープにも含まれない発見であり、削除せずアーカイブのみ取得して温存されている。

## 9. 裏が取れなかった点

- 公開リポジトリの履歴から除去した内容が、GitHub 側のサーバ内部の保持期間においてどれだけ残るかは確認できない。フォーク・PR が存在しないため実害はないと判断している。
- Kanidm と Garage の永続ボリュームが実際にどの k3s ノード上に配置されているかは、固定を確認していない。
- Kanidm の PV および Garage の静的 PV が実際にどの k3s ノード (150/151/152) に配置されているかは、`WaitForFirstConsumer` によるスケジューリング結果に依存し、本書では固定していない。ノードごとの PBS 対象一覧 (150,151,152 いずれも対象) に含まれるため保護経路の有無自体には影響しないが、特定のノード障害時にどのワークロードが影響を受けるかの一覧化は本書の範囲外とした。
