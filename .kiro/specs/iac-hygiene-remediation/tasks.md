# Implementation Plan

適用は design.md の Migration Strategy が定める段階に従う。タスク番号の並びと段階の対応は以下のとおり。

- 段階 0: タスク 2.1 → タスク 1
- 段階 0.5: タスク 2.2 - 2.6、タスク 6.1、タスク 6.2、タスク 28.1
- 段階 1: タスク 15 (15.6 を除く) → タスク 18.1 → タスク 25 → タスク 27 → タスク 12.1 → タスク 3 - 10 (6.1 と 6.2 を除く) → タスク 15.6
- 段階 2: タスク 11、12.2 - 12.6、13、14、16、17、18.2、19 (19.3 のうちブランチ保護を除く)、20、26、28.2、28.3、29
- 段階 3: タスク 21、タスク 24、19.3 のうちブランチ保護、およびタスク 9.1 のうち spec 成果物の追跡
- 段階 4: タスク 22
- タスク 23 は全段階完了後の最終検証であり、タスク 24 から 29 の結果も対象に含む

段階 1 の内部は、バックアップの再構築 (15) と保護アノテーションの付与 (18.1) を削除より前に置く。防御機構と保全手段を、それらが守る削除より後に置かない。認証基盤の撤去 (25) を削除群の先頭に置く。管理者初期パスワードが既定値のまま外部に公開されており、段階 1 で解消される事項の中で最も影響が大きいため。

既存のバックアップ成果物の除去 (15.6) は段階 1 の末尾に置く。当該成果物は再構築 (15.4) が復元可能な成果物を生成するまでの間、クラスタ上に現存する唯一の復元可能な成果物でありうる。代替が立つ前に除去すると、成果物がゼロの窓が段階 1 の削除群と重なる。

実機のゲストの列挙 (28.1) を段階 0.5 に前倒しする。バックアップ対象一覧の一本化 (15.5) が、列挙されていないゲストを対象外として恒久化するため、列挙は一本化より前に置く。冗長性を持たない物理ディスクを直接占有し、かつバックアップの対象にも含まれていないゲストの保全方針の決定は、段階 1 の完了条件に含める。

ブランチ保護の設定 (19.3 の該当項目) を段階 3 の履歴書き換え (21.3) の後に置く。段階 2 で有効化すると、既定ブランチへの force push を伴う 21.3 が実行できない。

段階 2 の認証基盤の構築 (26) は、段階 1 の撤去 (25) の完了と段階 0.5 の到達性回復 (2.3) の双方に依存する。

`(P)` は直前の同階層タスクと並行実行できることを示す。段階をまたぐ並行実行は行わない。停止を許可する点は段階の境界とする。段階の途中で停止せざるを得ない場合の扱いは要件 12.16 に従う。

- [x] 1. 停止中の公開サービスを復旧する

- [x] 1.1 証明書の失効状態を確定し応急復旧する
  - オリジンが提示する証明書の対象ホスト名と有効期限を確認し、ゾーンの SSL 検証設定との関係を確定する
  - 有効な証明書をオリジンに配置し、終端プロセスに読み込ませる
  - 公開ホスト名への外部からの HTTPS 要求が正常な応答を返すことを確認する
  - _Requirements: 15.1, 15.8_
  - _Boundary: EdgeCertificateSupply_
  - _Depends: 2.1_

- [x] 1.2 エッジホスト上に証明書の取得と更新を確立する
  - 証明書の供給をエッジホスト上で完結させ、他ホストからの配布に依存しない状態にする
  - 更新を要する機構について、検証方式をプロキシ経由のホスト名でも成立する経路とする
  - 更新後に終端プロセスが新しい証明書を読み込むこと、更新の失敗が検知できることを確認する
  - 更新を強制実行して成功することを確認する
  - 対象ホスト名の集合を、配信先の移設後もエッジホストが終端し続けるホスト名すべてを包含する形で定義する
  - _Requirements: 15.2, 15.3, 15.6, 15.9_
  - _Boundary: EdgeCertificateSupply_

- [x] 1.3 証明書の発行系を単一にし配布経路の残骸を除去する
  - 同一ドメインに対して並走している既存の発行系を撤去する
  - 到達不能な変数によって恒久的にスキップされる配布処理と、参照されない配布関連の変数を削除する
  - 撤去後も証明書の供給が継続することを確認する
  - _Requirements: 15.4, 15.5, 15.7_
  - _Boundary: EdgeCertificateSupply_

- [x] 1.4 供給機構をホスト名ごとに割り当て、ロールの定義として保持する
  - プロキシを経由して配信されるホスト名に、プロキシ元の認証局が発行する証明書を割り当てる
  - プロキシを経由しないホスト名と管理ゾーン外のホスト名に、公開的に信頼される証明書を DNS 検証で取得する経路を割り当てる
  - 各公開ホスト名についていずれの機構が供給するかを一覧として記録する
  - 双方の機構の設定と証明書の配置先をエッジロールのテンプレート配下に置き、ロールの適用によって失われない状態にする
  - 再適用しても証明書と設定が残ることの確認は段階 0 では実行できない。エッジロールの最初の実適用は段階 1 のタスク 3.2 であり、段階 0 の時点で再適用を行う経路が存在しない。確認はタスク 3.2 の適用時に行う
  - _Requirements: 15.11, 15.12, 15.13, 15.14_
  - _Boundary: EdgeCertificateSupply_
  - _Depends: 1.2_

- [x] 2. 構成管理の実行可能性と到達性を回復する

- [x] 2.1 供給経路でない暗号化ファイルを除去し playbook を起動可能にする
  - 段階 0 の最初のステップとして実施する。除去するまでインベントリのパースが失敗し、全ての play が起動しない
  - 供給経路として使用されていない Ansible Vault 暗号化ファイルを作業ツリーから削除する
  - 静的解析の設定ファイルを新設し、除外パスと適用プロファイルを定義する
  - 削除後にインベントリの一覧取得が成功し、エッジホストを対象とする playbook のチェック実行が成功することを確認する
  - _Requirements: 9.13, 9.14_

- [x] 2.2 Ansible の collection 依存を宣言する
  - 現在使用されている collection と、証明書情報の取得のために新たに必要となるものを依存として宣言する
  - バージョンは範囲指定とし、宣言ファイルの場所を README および steering が案内するパスと一致させる
  - 宣言ファイルから依存を導入する手順が実際に成功することを確認する
  - _Requirements: 4.12_

- [x] 2.3 到達できないコンテナへ公開鍵を注入する
  - 手元の鍵で到達しないコンテナ 2 件へ、収容元の仮想化基盤ノードから公開鍵を注入する。仮想化基盤のコンソールへの直接操作を要しない手段で行う
  - 既存の認可済み公開鍵を置き換えず追加する
  - インベントリの接続ユーザーが各ホストに実在するアカウントを指していることを確認する
  - インベントリに定義された全ホストに対する疎通確認が成功することを確認する
  - _Requirements: 17.1, 17.2, 17.6, 17.7, 17.8_
  - _Boundary: HostReachability_

- [x] 2.4 インベントリのグループ構成を整合させる
  - ホスト名とグループ名の衝突を解消する
  - 制御プレーンと agent を判別可能なグループ構成にする
  - ArgoCD の導入対象を制御プレーンに限定する
  - 実行時に名前衝突の警告が出ないことを確認する
  - _Requirements: 17.3, 17.4, 17.5_
  - _Boundary: HostReachability_

- [x] 2.5 エッジホストに対するロールをドライランで完走可能にする
  - 実機に存在しないパッケージを前提とするタスクを、前提の導入または当該タスクの除去により解消する
  - ロールをチェックモードと差分表示で実行し、エッジホストに対して最後まで完走することを確認する。この段階では実適用を行わない
  - 実行には become が要り、当該ホストの sudo はパスワードを要求する。昇格用のパスワードが環境変数経由で解決されることを前提条件として確認する
  - 差分の出力に現れる全項目について、実機にのみ存在する設定を失わせるか定義側に取り込むかの判断を記録する
  - 実機のリバースプロキシ設定ファイルは定義から生成された時点より前に凍結されており、メール用の中継定義が埋まった状態で現に外部からの接続を受けている。当該定義を「テンプレートが空レンダリングだから実機も空」とみなさない。差分の判定対象に含める
  - 現行の設定ファイルを退避し、稼働中の中継定義の内容を記録する。実適用によって失われる内容を定義側から復元できないため、退避を実適用の前提条件とする
  - 実適用は段階 1 でメール基盤の撤去と同一の適用単位として行う
  - _Requirements: 16.1, 16.2, 16.3, 4.5, 4.16_
  - _Boundary: EdgeHostAlignment_

- [x] 2.6 接続鍵の供給と配布を定義に載せる
  - インベントリが鍵をパスで指定している状態を解消する。パスは鍵の同一性を固定せず、同じパスが実行環境ごとに異なる鍵へ解決されるため、到達性が再現しない
  - 接続に用いる秘密鍵をシークレット管理基盤に登録し、そこを単一の情報源として供給する。いずれの実行環境からも同一の鍵が供給される状態にする。リポジトリと作業ツリーに平文で保持しない
  - 対象ホストの認可済み公開鍵を宣言的に定義し、インベントリ上の全ホストへ適用する。手元に秘密鍵の無い古い鍵のみを認可している 2 コンテナもこの適用対象に含める
  - 定義に現れない既存の認可済み公開鍵の扱いを、適用の前に決定する
  - 定義を 2 回適用し、2 回目に変更が報告されないことを確認する
  - 手元の既定名の鍵を退避した状態でも全ホストへの疎通確認が成功することを確認する
  - _Requirements: 17.9, 17.10, 17.11_
  - _Boundary: HostReachability_
  - _Depends: 2.3_

- [x] 3. クラスタ上の孤児と撤去対象の除去

- [x] 3.1 クラスタ上の孤児リソースを列挙して除去する
  - クラスタ上の全ワークロードを、管理下にあるかと Git 上に定義が存在するかで分類し、孤児の一覧を作成する
  - 既定の名前空間に存在する重複した認証基盤のワークロードとサービス、完了済みの診断用 Pod、撤去済みと記録されている封緘シークレット機構の実体を削除する
  - 削除前に各リソースの永続データの有無を確認して一覧に含める。あわせて各項目のデータの再構築元 (Git 上の定義、外部からの再取得、再生成) を 1 行で特定する。再構築元を特定できないものは削除の対象から外す
  - バックアップの成果物を保持するオブジェクトストレージの永続ボリュームは、「クラスタ内の永続データは復旧対象ではない」の例外として扱い、削除の対象に含めない
  - 実行前に削除対象と影響範囲を運用者へ提示し、承認を得てから削除する
  - カスタムリソース定義の削除は、対象型のインスタンスが存在しないことを再確認したうえで、他の削除と分離した単独の適用として行う
  - 除去後の再列挙で、管理下にないワークロードが残っていないことを確認する
  - _Requirements: 14.1, 14.2, 14.3, 14.4, 14.5, 14.6, 14.7, 25.6, 12.17_
  - _Boundary: ClusterOrphanCleanup_
  - _Depends: 15.4, 18.1_

- [x] 3.2 mailu を撤去しエッジロールを実適用する
  - クラスタ上の mailu 関連リソースを列挙し、永続データを持つものを一覧に含める。クラスタ内の永続データは復旧対象ではないため保全手順を伴わない
  - 管理外の永続ボリューム要求を除去する前に、対象と影響範囲を運用者へ提示し承認を得る
  - mailu のマニフェスト一式と、適用されていない個別アプリケーション定義を削除する
  - 管理外にある永続ボリューム要求を手動で除去する
  - メール向けの DNS レコードについて、将来のメール基盤で再利用するものと削除するものを区別し、後者を削除する
  - エッジロールの実適用を本タスクと同一の適用単位で行う。ロールの適用でメール用の待受が消えるため、マニフェストの削除と順序を分けない
  - 撤去後に mailu の名前空間が存在せず、メール向けホスト名への接続が確立しないこと、ロールが実機に対して完走することを確認する
  - 適用の前に、タスク 2.5 で退避した現行の設定ファイルが手元にあることを確認する
  - 適用後もタスク 1 で復旧した証明書と設定が残っており、エッジホストが終端し続ける公開ホスト名への外部からの HTTPS 要求が正常な応答を返すことを確認する。本適用はエッジロールの最初の実適用であり、段階 0 の復旧が定義側に取り込めていない場合はここで失われる
  - 適用後に、撤去対象と決めた経路以外の公開経路が失われていないことを確認する。本適用は現に稼働しているメール中継の定義を消す。消える範囲を撤去対象と一致させ、意図せず閉じた経路がないことを確認する
  - 退避した中継定義について、撤去する範囲と後続のメール基盤へ引き継ぐ範囲を区別して記録する。後者は当該基盤の中継定義の雛形として扱う
  - _Requirements: 5.1, 5.2, 5.3, 5.4, 5.6, 5.7, 16.1, 15.14, 4.16, 4.17_
  - _Boundary: MailuDecommission, EdgeHostAlignment_
  - _Depends: 3.1, 12.1_

- [x] 3.3 (P) xrayvpn を停止し未適用マニフェストを削除する
  - 稼働するコンテナを持たない状態にし、マニフェストは保持して復帰が設定値の変更のみで完了する状態を維持する
  - 登録されていない 8 個のマニフェストを削除する。これにより平文のクライアント識別子と、存在しないシークレットへの参照が同時に解消される
  - エッジの SNI 分岐定義と、外部公開されている DNS レコードを閉じる
  - 停止時に変更した設定値の一覧を復帰手順として記録する
  - 停止後に Pod が存在せず、外部公開ホスト名への TLS 接続が確立しないことを確認する
  - _Requirements: 13.1, 13.2, 13.3, 13.4, 13.5, 13.6, 1.3, 4.1, 4.2_
  - _Boundary: XrayvpnSuspension, EdgeProxyRepair_

- [x] 4. 重複した制御機構と未使用資産の解消

- [x] 4.1 重複したアプリケーション生成定義を解消する

  - 恒久的に失敗し続けている生成定義を除去する

- [x] 4.3 (P) 壊れた参照と不要になった資産を除去する

  - 導入完了後に不要となる初期認証情報と、廃止済み機構のための設定を削除する
  - 中身を持たない名前空間を削除する
  - 管理ゾーン上の検証用レコードのうち、対応する発行系を失ったものを除去する。Terraform が当該種別を管理対象外と宣言しているため、除去の担当を定めない限り残り続ける
  - 各ワークロードの履歴保持世代に上限を設定する
  - インスタンスを持たないカスタムリソース定義について、上流の導入物に付随するものと単独で導入されたものを区別し、保持の是非を判断して記録する。除去する場合は他の削除と分離した単独の適用として行う
  - 除去後に全アプリケーションが正常な同期状態を維持することを確認する

- [x] 28.3 稼働中のデータベースホストを定義に載せ、不要なデータを整理する
  - 当該ゲストは本 spec のいずれのタスクの対象にもなっておらず、定義上の位置付けを持たない。保持しているデータベースのうち一つは、現に稼働しているサービスの本番データであり、当該サービスは GitOps の同期元でもある。残りは撤去済みのサービスに属する
  - 当該ゲストが複数の系統に接続を持つことを前提に、参照側が用いる接続先と、退避の経路が用いる接続先の双方を特定する。片方の接続先だけを見て同一性を判定しない
  - 稼働中のサービスの本番データについて、移行するか現在の場所に留めるかを決める。移行を選ぶ場合、移行の前後で当該サービスが継続することを確認し、失敗時に元の場所へ戻せる状態を保つ

- [x] 28.4 バージョン管理サービスのデータベースを当該サービスと同一のゲストへ集約する
  - 現在、当該サービスの本体と、そのデータベースが別々のゲストに分かれている。ゲストレベルの退避はゲスト単位に取られるため、両者の退避時点が揃わない
  - 集約先は当該サービス本体が稼働するゲストとする。移行元と同一の実装系統を用い、系統をまたぐ変換を行わない
  - クラスタ上の論理レプリケーション基盤は集約先として採らない。当該基盤の継続的な退避先が、クラスタのノードと同一の記憶装置上にあり、冗長化もされていないため、ゲストレベルの退避より強い保護にならない
  - 移行の前に、移行元のデータを復元可能な形で退避する
  - 移行の前後で当該サービスが継続することを確認し、失敗時に元の格納先へ戻せる状態を保つ
  - 移行後に、移行前後でデータの同一性が保たれていることを、件数だけでなく内容の照合により確認する
  - 論理的な形式での定期的な退避を仕組みとして持つ。退避先は当該ゲストの外とする
  - 接続情報および資格情報の供給元をシークレット管理基盤に一本化する
  - 移行元のゲストに残った定義、データベース、資格情報を整理する。当該ゲストが他に役割を持たなくなる場合、ゲスト自体の扱いを決める

  - _Boundary: ProxmoxGuestAlignment_
  - _Depends: 28.3_

- [x] 28.5 オブジェクト記憶の実体を保護対象と別の記憶装置へ分離する
  - 当該記憶は、クラスタ上の論理レプリケーション基盤の継続的な退避先である。現在その実体は、クラスタのノードの起動用記憶装置そのものの上にあり、退避が守ろうとしている対象と同一の記憶装置を共有している
  - 索引と実体を別の記憶装置に分ける。索引は小さな書き込みが不規則に生じ遅延に敏感であるため速い記憶装置に置き、実体は逐次的な書き込みが主であるため容量の大きい記憶装置に置く
  - 実体の置き場所を、クラスタのノードの起動用記憶装置から外す
  - 当該記憶は複製数が 1 であり、単一の系統のみで稼働している。冗長化の要否を判断し、採らない場合はその理由と受容する損失の範囲を記録する
  - 記憶量の要求が下位の記憶装置に対して強制されない構成であることを前提に、容量の枯渇を検知できる状態にする
  - 定義が失われた際に実体が無条件に消去される仕組みであることを踏まえ、消去を防ぐ設定が有効であることを確認する。定義を経由しない直接の削除に対しては保護がないことを記録する
  - 分離の前後で、継続的な退避が機能し、そこからの復元が成立することを確認する
  - _Requirements: 28.11, 28.12, 28.13, 28.14, 28.15, 19.1_
  - _Boundary: ProxmoxGuestAlignment, WorkloadGuardrails_
  - _Depends: 28.4_

- [x] 28.6 運用者が除去を指示したゲストを取り除く
  - 対象は、推論モデルの実行環境として置かれ、定義を持たないまま稼働している一つのゲストである。運用者が除去を明示的に指示した

  - 除去の後、実機のゲスト一覧と定義側の記述を一致させる
