# Requirements Document

## Scope Snapshot

ホームラボ IaC を構成する 3 リポジトリ (`my-home-network`: Terraform / Ansible / スクリプト、`gitops-apps`: ArgoCD が同期する Kubernetes マニフェスト、`portfolio`: `fickledev.com` を配信する Next.js サイト) の品質欠陥を一括是正する。gitops-apps および portfolio への変更も本 spec のタスクとして管理する。

是正対象は以下に分類される。

- **セキュリティとシークレット** — マニフェストおよび Helm values 上の平文認証情報、git 履歴に混入した k3s トークンとデータベース資格情報、安全でない既定値 (TLS 検証のスキップ、過大なパーミッション、機微指定の欠落)、シークレット供給経路の三重帳簿、シークレットスキャンの検出範囲。
- **動作していないコード** — Kustomize / Helm のレンダリング対象に含まれないマニフェスト、解決不能な Ingress バックエンド、未定義変数に依存し常に空となるテンプレート、差分抑止によって反映されない Terraform の定義、接続情報を持たないインベントリのホスト。
- **撤去** — mailu、既存の認証基盤とその LDAP クライアント設定、Kubernetes Dashboard、および xrayvpn の稼働停止。撤去に伴う DNS レコード、公開経路、リバースプロキシ定義の整理を含む。
- **重複と情報源の分散** — ディスクプロビジョニング、証明書ファイルの取り回し、API リクエスト本文、DNS レコード定義の重複。ホストアドレス、ゾーン名、リポジトリ URL、プロジェクト識別子の複数箇所定義。
- **冪等性とエラーハンドリング** — 一度限りの移行処理の永住、無条件に固定された成否判定、失敗の握り潰し、起動のたびに外部から取得する非再現な構成。
- **デッドコードと残存アーティファクト** — 参照されない変数と恒久的に無効化された処理、移行完了済みのスクリプト、ローカル state と調査用出力、放置された枝。
- **GitOps の品質ガード** — リソース要求と上限、稼働状態の検査、コンテナ実行時のセキュリティ設定、イメージの固定、永続データを持つアプリケーションの削除防御。
- **規約とドキュメント** — コメント規約、README と steering の実態との乖離。

あわせて、認証基盤を Kanidm 単体として構築し直し、公開サイトの配信を Cloudflare Workers へ移設し、機能していないバックアップ基盤を定義から再構築する。エッジホストの証明書供給、管理対象ホストへの到達性、仮想化基盤上のゲストと定義の対応も本 spec の対象とする。

## Introduction

本 spec は、ホームラボ IaC を構成する 3 リポジトリ (`my-home-network`: Terraform / Ansible / スクリプト、`gitops-apps`: ArgoCD が同期する Kubernetes マニフェスト、`portfolio`: `fickledev.com` を配信する Next.js サイト) に対して実施した監査で検出された約 120 件の品質欠陥を是正する。

対象は新機能の追加ではなく、既存コードの是正である。検出事項は、実際に危険な状態にあるもの (平文シークレット、漏洩済みトークンの未ローテーション、安全でない既定値)、実際に動作していないもの (未参照マニフェスト、未定義変数に依存するテンプレート、解決不能な Ingress)、将来の変更コストを押し上げるもの (同一ロジックの三重実装、情報源の四重定義、デッドコード)、および規約・ドキュメントの実態との乖離に分類される。

あわせて、Kubernetes 上で稼働する mailu を完全に撤去する。メール基盤は VPS 上の docker-mailserver (DMS) として作り直す方針だが、その構築は本 spec のスコープ外であり、本 spec は撤去と、撤去に伴う周辺定義 (DNS レコード、リバースプロキシのメール経路設定) の整理までを担う。

同様に、当面利用しない xrayvpn を停止する。こちらは撤去ではなく、定義を保持したまま稼働を止め、外部からの経路も同時に閉じる。復帰が設定値の変更のみで完了することを条件とする。

認証基盤は Kanidm 単体とする。既存の authentik と、そのクライアントとして構成された `sssd` ロールを撤去し、Kanidm を k3s 上に構築したうえで Gitea、ArgoCD、NAS のログイン統合、Home Assistant、Garage の UI、Guacamole を認証の背後に置く。NAS の POSIX 統合は `kanidm-unixd` が担う。

Kubernetes Dashboard は撤去し、クラスタの管理操作の手段を kubeconfig と端末クライアントに一本化する。

稼働中のホームラボが対象であり、ArgoCD の syncPolicy が全アプリケーション一律で `prune: true` / `selfHeal: true` であるため、マニフェストの削除はクラスタ上のリソース削除に直結する。またディスクプロビジョニングの共通化はデータ破壊を伴いうる。したがって本 spec は「正しく直すこと」と同等に「壊さずに直すこと」を要件として扱う。

  - mailu の撤去と、それに伴う DNS レコードおよび `vps_proxy` ロールのメール関連定義の整理
  - 既存の認証基盤と LDAP クライアント設定の撤去、Kanidm による認証基盤の構築、および対象サービスの認証統合
  - Kubernetes Dashboard の撤去と、それに伴う公開経路およびドキュメントの整理
  - xrayvpn の稼働停止と、それに伴う `vps_proxy` ロールのバックエンド経路の無効化
  - クラスタ上に存在し Git 上に対応する定義を持たない孤児リソースの除去
  - 漏洩済み k3s トークンのローテーション、およびその影響評価
  - `portfolio` リポジトリ (`/home/musashi/Documents/develop/portfolio`) の配信基盤の移設、および移設に伴う DNS レコード・`vps_proxy` ロール・旧配信元コンテナの整理
- **Out of scope**:
  - docker-mailserver (DMS) の設計・構築・移行 (別 spec とする)
  - 新規ワークロードの追加、既存ワークロードの機能拡張
  - Kubernetes クラスタそのものの構成変更 (k3s トークンローテーションに不可避な範囲を除く)

- **Adjacent expectations**:
  - steering (`.kiro/steering/structure.md`) は「本リポジトリは `gitops-apps` の内容を管理しない」と定義している。本 spec は例外的に 3 リポジトリの是正を 1 本の spec で管理するため、この境界の扱いを steering 側で明示する必要がある
  - `gitops-apps` は自前の `.kiro/specs/` を持ち、`autonomous-parallel-dev-platform` が requirements 段階で並走している。本 spec を先に完了させ、要件 10 が定める品質ガードを新基盤が従う規約として明文化する
  - `apps/argocd/applicationset.yaml` に除外定義は存在しない。`apps/` 配下に置いたディレクトリは共有基盤的なものも含めて必ず Application として生成される。要件 10.9 / 10.10 の生成対象の制御は、この足場を新設したうえで成立する
  - クラスタ上には同一のリポジトリの同一パスを走査する ApplicationSet が 2 つ稼働している。要件 21.1 が定める重複はこれを指す
  - steering (`.kiro/steering/tech.md`) は `vault.yml.example` を「移行前の変数名一覧として残置」と定義している。監査が指摘した「シークレット管理の三重帳簿」は、この意図が README およびファイル内容から読み取れないことに起因する。単純削除ではなく意図の明示または撤去のいずれかを選択する必要がある
  - steering (`.kiro/steering/tech.md`) 自身が、存在しない `collections/requirements.yml` を利用手順として記載している。ドキュメント側の是正は steering の是正を伴う

## Requirements

### Requirement 1: 平文シークレットと漏洩済み認証情報の解消

**Objective:** ホームラボ管理者として、リポジトリおよびクラスタ上に平文の認証情報が存在しない状態にしたい。それにより、リポジトリの参照権限がそのまま各サービスへの侵入経路になることを防げる。

#### Acceptance Criteria

1. The `gitops-apps` リポジトリ shall Kubernetes マニフェストおよび Helm values に、認証情報として機能する平文値 (パスワード、トークン、クライアント UUID) を含まない。
2. If 管理者初期パスワードを平文で保持するワークロードが要件 25 の撤去対象に含まれる場合, then the `gitops-apps` リポジトリ shall 当該値に対する供給経路を新設せず、撤去をもって平文の解消とする。
3. When xrayvpn のクライアント識別子が必要になる場合, the `xrayvpn` アプリケーション shall Infisical 参照版の設定テンプレートのみを供給経路として使用し、平文 UUID を含む ConfigMap を保持しない。
4. The IaC 保守担当 shall git 履歴にコミット済みの k3s トークンをローテーションし、`ansible/inventory/host_vars/k3s-server/main.yml` の未対応を示す注記を解消する。
5. When k3s トークンをローテーションする場合, the IaC 保守担当 shall 事前に影響範囲 (再参加が必要なノード、想定ダウンタイム、失敗時の復旧手順) を文書化し、実施可否の判断材料を提示する。
6. The IaC 保守担当 shall git 履歴から漏洩した認証情報を含むオブジェクトを除去し、リモートリポジトリの公開面に残存しない状態にする。除去の対象は k3s トークンが混入した 26 コミットと、暗号化されずにコミットされたデータベース資格情報が混入した 3 コミットの双方とする。
7. When git 履歴を書き換える場合, the IaC 保守担当 shall 書き換えによって失われる参照 (コミット識別子、既存のクローン、リモート側に残るキャッシュ) への対処を事前に整理する。
8. The IaC 保守担当 shall 履歴の書き換えと認証情報のローテーションの双方を完了させる。いずれか一方のみでは完了とみなさない。
9. The IaC 保守担当 shall 暗号化されずにコミットされたデータベース資格情報をローテーションする。
10. If いずれかの認証情報がローテーション不可能である場合, then the IaC 保守担当 shall その理由と残存リスクを記録し、当該値への到達経路を最小化する代替策を講じる。
11. When 本 spec が新しい認証情報を発行する場合, the IaC 保守担当 shall 当該値をローカルで生成し、シークレット管理基盤へ登録したうえで供給する。対象はデータベース資格情報および k3s のクラスタトークンとする。

### Requirement 2: シークレットスキャンの検出範囲の是正

**Objective:** ホームラボ管理者として、シークレットスキャンが実際に守るべき対象を検査している状態にしたい。それにより、防御機構が存在するのに漏洩を見逃す状態を解消できる。

#### Acceptance Criteria

1. The `secret-scan` ワークフロー shall 作業ツリーに加えて git 履歴を走査対象に含める。
2. When 履歴を走査対象に含めた場合, the `secret-scan` ワークフロー shall 検出をゼロで完了する。許可リストによる除外で検出を回避しない。
3. If シークレットスキャンが検出を報告した場合, then the `secret-scan` ワークフロー shall 該当ジョブを失敗させる。
4. The `secret-scan` ワークフロー shall 検出内容を出力する際にシークレット値そのものを露出しない。
5. The `secret-scan` ワークフロー shall 履歴を走査するために必要な範囲でリポジトリを取得する。
6. The `secret-scan` ワークフロー shall 走査の挙動を指定する引数が実際に実行へ反映される呼び出し方式を用いる。現行の呼び出しは、入力を宣言していない上流アクションへ引数を渡しており、指定が実行に反映されない。走査範囲の是正は、引数の値の変更ではなく反映される呼び出し方式への変更によって行う。

### Requirement 3: 安全でない既定値の是正

**Objective:** ホームラボ管理者として、設定を明示しなかった場合に安全側へ倒れる状態にしたい。それにより、設定漏れがそのまま脆弱性にならないようにできる。

#### Acceptance Criteria

1. The Terraform 設定 shall Proxmox API の TLS 検証をスキップする変数の既定値を、検証を有効にする側に設定する。
2. The Terraform 設定 shall 認証情報を保持する変数すべてに機微指定を付与し、plan / apply の出力に平文で現れないようにする。
3. The Terraform 設定 shall 認証情報を保持する変数に既定値を与えず、未設定時は明示的なエラーとして検出されるようにする。
4. The `gitea` ロール shall Gitea のデータディレクトリを、所有者以外に書き込みを許可しないパーミッションで作成する。
5. If バックエンドへの TLS 検証をスキップする設定を持つアプリケーションが要件 27 の撤去対象である場合, then the `gitops-apps` リポジトリ shall 撤去をもって当該設定の解消とし、同等の設定を他のアプリケーションへ持ち込まない。
6. The `garage` アプリケーション shall Secret ファイルの権限チェックを無効化する設定について、必要性の根拠を持つか、または当該設定を除去する。
7. If 許可範囲が名称の示す発信元と一致しない NetworkPolicy を持つチャートが要件 25 の撤去対象である場合, then the `gitops-apps` リポジトリ shall 撤去をもって解消とし、当該 NetworkPolicy を再定義しない。
8. The `cluster-issuer` アプリケーション shall 本番 ACME Issuer の連絡先メールアドレスに、実在する到達可能な値を設定する。

### Requirement 4: 動作していないコードの修復または除去

**Objective:** ホームラボ管理者として、リポジトリ上のコードが実際に効果を持っている状態にしたい。それにより、「設定したつもりで効いていない」状態と、それに起因する誤った安心を排除できる。

#### Acceptance Criteria

1. The `gitops-apps` リポジトリ shall すべてのマニフェストファイルについて、Kustomize の resources もしくは Helm チャートのテンプレートとして実際にレンダリングされる状態にするか、または当該ファイルを削除する。
2. When `xrayvpn` アプリケーションの構成を確定する場合, the IaC 保守担当 shall 現に稼働している構成を特定し、それ以外の未参照ファイルを削除する。
3. The `garage` チャート shall Ingress のバックエンドとして、同チャート内に存在し、かつポート番号が一致する Service のみを参照する。
4. The `garage` チャート shall 各コンテナに対して、そのコンテナが実際に必要とする設定ファイルのみをマウントする。
5. The `vps_proxy` ロール shall HAProxy 設定テンプレートが参照する変数について、定義済みの変数のみを参照する。テンプレートの当該箇所が空レンダリングとなる事実は、実機の設定が空であることを意味しない。実機の設定ファイルは定義から生成された時点より前に凍結されており、メール用の中継定義が埋まった状態で現に稼働している。
6. If HAProxy のメール経路定義が mailu 撤去後に不要となる場合, then the `vps_proxy` ロール shall 当該定義および付随する証明書バンドル生成処理を削除する。
7. The `vm` モジュール shall ディスク定義の変更が `terraform apply` に反映される状態にする。
8. The `container` モジュール shall SSH 公開鍵の変更が `terraform apply` に反映される状態にする。
9. If `ignore_changes` の指定を維持する必要がある場合, then the Terraform モジュール shall 維持が必要な属性のみを対象とし、その理由をコード上に残す。
10. The Ansible インベントリ shall グループに所属するすべてのホストについて、接続情報を含む変数を定義済みにするか、または当該ホストをグループから除去する。
11. If 先行タスクが条件によりスキップされうる場合, then the `letsencrypt` ロール shall その結果を参照する後続タスクで未定義値を安全に扱う。
12. The Ansible 設定 shall 必要な collection 依存を宣言したファイルを保持し、ドキュメントおよび steering の記載と一致させる。
13. The `k3s` グループ変数 shall `rlex.k3s` ロールが期待する型に一致する値を渡す。対象は agent 側の追加引数の変数であり、ロールの既定値が文字列であるのに対しインベントリがリストを渡している。master 側の同名の変数はロールの既定値もリストであり型は一致している。
14. The `rlex.k3s` ロール shall 取得元を Galaxy 経由か in-tree のいずれか一方に定め、二重定義を解消する。
15. The `vm` モジュール shall 追加ボリュームの割当先をリスト位置から導出しない。リストの要素を除去したときに、残るボリュームの割当先が変化しない状態にする。本項は要件 18.8 の確認を成立させる前提であり、要件 18 の領域解放に先行して満たす。
16. When エッジホストへロールを実適用する場合, the IaC 保守担当 shall 適用の前に実機の現行設定ファイルを退避する。当該ファイルは定義から生成されておらず、適用によって失われる内容を定義側から復元できない。
17. The IaC 保守担当 shall 実機の現行設定が保持するメール中継の定義を、撤去する範囲と後続のメール基盤へ引き継ぐ範囲に区別して記録する。退避した内容を当該基盤の中継定義の雛形として扱う。

### Requirement 5: mailu の完全撤去

**Objective:** ホームラボ管理者として、Kubernetes 上の mailu を痕跡なく撤去したい。それにより、二重定義による同期の競合を解消し、VPS 上の DMS へ移行する前提を整えられる。

#### Acceptance Criteria

1. The `gitops-apps` リポジトリ shall `apps/mailu/` 配下のすべてのファイルおよび `argocd/mailu-application.yaml` を削除する。
2. When mailu のマニフェストを削除する場合, the IaC 保守担当 shall 削除前に、クラスタ上の mailu 関連リソースのうち保全が必要なもの (永続ボリューム、証明書、Secret) を列挙し、保全または破棄の判断を記録する。
3. While ApplicationSet の syncPolicy が `prune: true` である間, when mailu の Application 生成元ディレクトリが削除された場合, the IaC 保守担当 shall クラスタ上の mailu 名前空間およびリソースが削除される挙動を前提として作業手順を組む。
4. The Terraform 設定 shall mailu 向けの DNS レコードについて、DMS 移行時に再利用するものと削除するものを区別し、後者を削除する。
5. The mailu 向けに定義され未参照であるメール関連変数の削除 shall 要件 4.6 が定める削除に含める。本項は当該削除が mailu 撤去の完了条件であることのみを定め、独立した是正を求めない。
6. The `my-home-network` リポジトリ shall README およびネットワーク構成の記述から mailu への言及を除去し、メール基盤が未構築であることを現状として記載する。
7. If mailu 撤去後に残存するリソースがクラスタ上に確認された場合, then the IaC 保守担当 shall 当該リソースを手動で除去し、除去内容を記録する。

### Requirement 6: 重複実装の共通化

**Objective:** ホームラボ管理者として、同一のロジックが 1 箇所にのみ存在する状態にしたい。それにより、修正が一部の複製にしか反映されないという不整合を防げる。

#### Acceptance Criteria

1. The Ansible 実装 shall ディスクの検出・パーティション作成・ファイルシステム作成・マウントのロジックを、単一の再利用可能な role として保持する。
2. The Ansible 実装 shall tasks ファイルを `playbooks/` 配下に配置しない。
3. When 既存の利用箇所を共通実装へ移行する場合, the IaC 保守担当 shall 移行前後で生成される設定が等価であることを、検証可能な手段で確認する。
4. The Ansible 実装 shall 対象デバイスを一意に特定できることを検証する既存の事前条件チェックを、共通化後も保持する。
5. If ディスクプロビジョニングの共通実装が対象デバイスを特定できない場合, then the Ansible 実装 shall 処理を中断し、破壊的操作を実行しない。
6. The `my-home-network` リポジトリ shall 呼び出し元を持たず、参照する変数の定義も存在しないディスクプロビジョニング実装を保持しない。
7. The `letsencrypt` ロール shall 証明書ファイルと秘密鍵ファイルに対する同一処理を、ファイル種別を要素とする反復として表現する。
8. The `proxmox_backup` ロール shall バックアップジョブの作成と更新について、リクエスト本文の定義を共有する。
9. The `gitea` ロール shall ユーザー一覧の取得と判定について、同一処理の重複を解消する。
10. The `vps_proxy` ロール shall 旧コンテナの検査と削除について、対象を要素とする反復として表現する。
11. The `nas` ロール shall 同一内容のタスクを重複して定義しない。
12. The Terraform 設定 shall 属性が共通する DNS レコード群を、レコード名を要素とする反復として定義する。
13. If 主コンテナとワーカーコンテナで環境変数定義が重複するチャートが要件 25 の撤去対象である場合, then the `gitops-apps` リポジトリ shall 撤去をもって解消とし、当該重複に対する共通化を行わない。
14. The `gitops-apps` リポジトリ shall Infisical のシークレット同期定義について、共通する構造を単一の定義として共有する。
15. The `my-home-network` リポジトリ shall 同一の環境変数を role defaults と inventory の双方から読む重複を解消する。

### Requirement 7: 環境固有値の重複解消と不整合の検知

**Objective:** ホームラボ管理者として、環境固有値の定義箇所を減らし、減らせない重複については食い違いが検知される状態にしたい。それにより、片方だけ更新して構成が食い違う事故を防げる。

#### Acceptance Criteria

1. The `my-home-network` リポジトリ shall 各ホストの IP アドレスが重複定義されている箇所を、その用途とともに明示する。
2. The `my-home-network` リポジトリ shall 重複定義された IP アドレスの間に不整合が生じた場合、それを検知する手段を持つ。
3. When 不整合の検知を行う場合, the 検知手段 shall Terraform の管理対象外であるホストを判定対象から除外する。
4. The Terraform 設定 shall VPS の IPv4 / IPv6 アドレスを変数または locals として定義し、DNS レコード定義から参照する。
5. The Terraform 設定 shall 管理対象ゾーンのドメイン名を単一の定義箇所から参照する。
6. The `gitops-apps` リポジトリ shall Ingress のホスト名について、Helm チャートと Kustomize のいずれにおいても値の定義方法を統一する。
7. The `gitops-apps` リポジトリ shall Infisical のプロジェクト識別子を単一の定義箇所から参照する。
8. The 両リポジトリ shall Gitea リポジトリの URL を、リポジトリごとに単一の定義箇所から参照する。
9. If ArgoCD が読み込むマニフェストの性質上、値を変数として定義できない場合, then the `my-home-network` リポジトリ shall 当該箇所を要件 7.1 の重複一覧に含める。
10. The `argocd` ロール shall テンプレート内に直書きされた値を role defaults からの参照に置き換え、defaults を当該値の単一の定義箇所とする。
11. If 自環境固有のディレクトリ接続情報を role defaults に直書きするロールが要件 25 の撤去対象である場合, then the `my-home-network` リポジトリ shall 撤去をもって解消とし、当該接続情報を他の定義箇所へ再配置しない。
12. The Terraform 設定 shall 環境依存の値 (ゲートウェイ、DNS サーバー、テンプレート ID、ノード名、初期ユーザー名) に既定値を与えず、呼び出し側で明示させる。
13. The `gitops-apps` リポジトリ shall 永続ボリュームの StorageClass 指定を全アプリケーションで統一する。
14. When StorageClass を統一する場合, the `gitops-apps` リポジトリ shall 統一後に利用されなくなった StorageClass 定義を削除する。

### Requirement 8: 冪等性とエラーハンドリングの回復

**Objective:** ホームラボ管理者として、再実行しても結果が変わらず、失敗が失敗として報告される状態にしたい。それにより、実行結果を信頼して判断できるようになる。

#### Acceptance Criteria

1. The Ansible ロール shall 同一の入力に対して繰り返し実行しても、2 回目以降に変更を報告しない。
2. The Ansible ロール shall タスクの成否判定を無条件に固定しない。
3. If タスクが失敗した場合, then the Ansible ロール shall 当該失敗を報告し、後続の処理を継続しない。ただし失敗を許容する明示的な理由がある場合を除く。
4. When 失敗を許容する必要がある場合, the Ansible ロール shall 許容する失敗の条件を限定し、その理由をコード上に残す。
5. The `gitea` ロール shall 管理者ユーザーの作成に失敗した場合、既定でその失敗を報告する。
6. The `proxmox_backup` ロール shall API 呼び出しが失敗した場合に、シークレットを露出させずに原因を特定できる情報を提示する。出力の抑止を切り替える変数は既に存在するため、新たな変数化を求めない。本項が求めるのは、失敗時に原因が特定できる状態を既定で成立させることである。
7. The `nfs_client` ロール shall マウント状態の確認を、冪等なモジュールによる宣言に置き換える。
8. The `letsencrypt` ロール shall 証明書の有効期限判定を、外部コマンドの出力の手計算ではなく証明書情報を扱うモジュールで行う。
9. The `argocd` ロール shall リソースの待機を、単一の明示的なタイムアウトを持つ手段で行う。
10. The `vps_proxy` ロール shall 一度限りの移行処理を恒久的なタスクとして保持しない。
11. The `vps_proxy` ロール shall 実行環境の前提条件を検証するタスクを、その前提に依存するタスクより先に実行する。
12. The Ansible 設定 shall ホスト鍵の検証方針を単一の方式に定め、相互に無効化しあう設定を保持しない。
13. The Ansible 設定 shall 非推奨となった設定項目を使用しない。
14. The `garage` チャート shall 初期セットアップを、インラインシェルによる状態ポーリングに依存しない手段で行う。
15. The `garage` チャート shall バックアップ処理において、実行前の確認と実際の削除を重複して実行しない。
16. The `home-assistant` アプリケーション shall 起動時に外部から追加コンポーネントを取得する構成を、バージョンが固定され再現可能な手段に置き換えるか、または当該構成を除去する。
17. The `xrayvpn` アプリケーション shall 起動のたびにパッケージを導入する構成を除去する。
18. The `dump_cloudflare_config` スクリプト shall 処理の失敗を無視して続行しない。

### Requirement 9: デッドコードと残存アーティファクトの除去

**Objective:** ホームラボ管理者として、リポジトリに読む必要のないコードが残っていない状態にしたい。それにより、実装を読むときに何が生きているかを判断するコストをなくせる。

#### Acceptance Criteria

1. The Ansible ロール shall `defaults/` に、どこからも参照されない変数を保持しない。
2. The Ansible ロール shall 常に空となる反復処理および恒久的に無効化された処理を保持しない。
3. The Ansible インベントリ shall コメントアウトされたホスト定義を保持しない。
4. The Ansible playbook shall 実体を持たないプレースホルダを保持しない。ロールの適用を伴う playbook は、`tasks` が空であることのみをもってプレースホルダと判定しない。
5. The `site.yml` shall リポジトリ内のすべての playbook について、含める場合は明示的に含め、含めない場合はその playbook を単独実行用と位置づける。
6. The Terraform 設定 shall 参照されない変数宣言およびリソース定義を持たないファイルを保持しない。
7. The `my-home-network` リポジトリ shall 使用しないと明記された設定例ファイルを追跡対象に含めない。
8. The `my-home-network` リポジトリ shall 移行完了済みの一回限りのスクリプトについて、保持するか削除するかを決定し、保持する場合は未実装のオプションを除去する。
9. The `my-home-network` リポジトリ shall リモート state への移行完了後、機微情報を含むローカル state ファイルおよび調査用出力を作業ツリーから除去する。
10. The Kustomize に登録されないマニフェストおよび使用されていない Kubernetes リソース定義の除去 shall 要件 4.1 が定める判定に従う。本項は独立した是正を求めない。
11. The `gitops-apps` リポジトリ shall 同一設定の新旧 2 世代を併存させない。
12. The `gitops-apps` リポジトリ shall 実体を持たないファイルおよび空のワークフロー定義を保持しない。
13. The `my-home-network` リポジトリ shall 供給経路として使用しない Ansible Vault 暗号化ファイルを作業ツリーに保持しない。
14. If 当該ファイルを保持する必要がある場合, then the `my-home-network` リポジトリ shall 静的解析の対象から除外し、除外の理由を設定上で識別可能にする。

### Requirement 10: GitOps ワークロードの品質ガード確立

**Objective:** ホームラボ管理者として、クラスタ上のワークロードが再現可能で、異常時に検知・隔離される状態にしたい。それにより、1 つのワークロードの障害がノード全体に波及することを防げる。

#### Acceptance Criteria

1. The `gitops-apps` リポジトリ shall ArgoCD が管理するすべてのワークロードに対してリソース要求および上限を定義する。対象は梱包の出自を問わない。
2. The `gitops-apps` リポジトリ shall 本リポジトリで記述した長時間稼働ワークロードに対して稼働状態の検査を定義する。上流由来の配布物および上流チャートが生成するワークロードは、要件 10.12 の確認の対象とし、定義の注入を求めない。
3. The `gitops-apps` リポジトリ shall 本リポジトリで記述したワークロードに対してコンテナ実行時のセキュリティ設定を定義する。上流由来の配布物および上流チャートが生成するワークロードは、要件 10.12 の確認の対象とし、定義の注入を求めない。
4. The `gitops-apps` リポジトリ shall すべてのコンテナイメージを、可変でないタグまたはダイジェストで指定する。
5. The `gitops-apps` リポジトリ shall Helm チャートのメタデータに、実際に使用しているソフトウェアのバージョンを記載する。
6. The `gitops-apps` リポジトリ shall Helm の依存ロックファイルを追跡対象に含め、取得された依存チャートを追跡対象から除外する。
7. While ApplicationSet がすべてのアプリケーションに一律の syncPolicy を適用している間, the `gitops-apps` リポジトリ shall 永続データを持つアプリケーションについて、意図しない削除に対する防御手段を備える。
8. The `gitops-apps` リポジトリ shall ApplicationSet が定める名前空間規約に従うか、従わない場合はその理由をアプリケーション定義から判別可能にする。
9. The `gitops-apps` リポジトリ shall アプリケーションの定義方式 (Helm チャート / Kustomize / 上流マニフェストの取り込み) について選択基準を定め、各アプリケーションがいずれかに従う。
10. When 上流マニフェストを取り込む場合, the `gitops-apps` リポジトリ shall 取得元とバージョンを識別可能な形で記録する。
11. The `gitops-apps` リポジトリ shall 保守が終了したバージョンのコンテナイメージを使用しない。
12. Where 上流の定義が既にリソース要求と上限、稼働状態の検査、またはコンテナ実行時のセキュリティ設定を備えている場合, the `gitops-apps` リポジトリ shall 当該定義が要件を満たすことを確認し、重複する定義を追加しない。
13. If ワークロードに対してこれらの設定を与える手段が定義方式の側に存在しない場合, then the `gitops-apps` リポジトリ shall 対象と理由を記録し、未対応のまま記録を伴わない状態を残さない。

### Requirement 11: 規約・ドキュメント・steering の実態への同期

**Objective:** ホームラボ管理者として、ドキュメントと steering が現在の構成を正しく述べている状態にしたい。それにより、記述を信じて作業した結果が失敗することをなくせる。

#### Acceptance Criteria

1. The 両リポジトリ shall コード上のコメントについて、コードから復元できない情報のみを記載し、変更履歴、タスク識別子、spec への参照を含めない。
2. The `my-home-network` リポジトリ shall README から、解消済み事項の経緯を記した記述を除去する。
3. The 両リポジトリ shall ドキュメントに記載された構成が実装と一致することを確認し、一致しない記述を修正する。
4. The `my-home-network` リポジトリ shall README および steering に記載されたコマンド手順が、存在するファイルのみを参照するようにする。
5. The steering shall `gitops-apps` および `portfolio` リポジトリとの境界について、本 spec が 3 リポジトリを横断して管理する事実と整合する記述を持つ。
6. The steering shall シークレット供給経路の現状 (Infisical への集約、`vault.yml.example` の位置づけ) を、リポジトリの実態と一致させる。
7. If `vault.yml.example` を残置する場合, then the `my-home-network` リポジトリ shall 当該ファイルが変数名の一覧であり供給経路ではないことを、ファイル自体から判別可能にする。
8. The steering shall product.md に記載するワークロード一覧を、`gitops-apps` の実態と一致させる。
9. The `gitops-apps` の steering shall ApplicationSet の除外設定に関する記述を、`apps/argocd/applicationset.yaml` の実態と一致させる。
10. The steering shall `ansible-lint` および `terraform validate` の実行手順を、実際に成功する形で記載する。
11. The steering shall クラスタの管理操作の手段に関する規約が、ブラウザから提供される開発ワークスペースを対象としないことを明記する。

### Requirement 12: 段階的な適用と検証可能性

**Objective:** ホームラボ管理者として、是正を安全に適用できる単位に分割し、各段階で結果を確認したい。それにより、稼働中の環境を壊さずに是正を進められる。

#### Acceptance Criteria

1. The IaC 保守担当 shall 是正を、セキュリティ、動作していないコード、mailu 撤去、重複の共通化、その他の順で優先度付けして適用する。
2. The IaC 保守担当 shall 各是正単位について、適用前に検証手段を定め、適用後にその検証を実行する。
3. When クラスタ上のリソース削除を伴う変更を適用する場合, the IaC 保守担当 shall 事前に影響を受けるリソースを列挙して提示する。復旧対象と定めた永続データを持つリソースについては、あわせて保全手順を実施する。
4. When ディスクに対する破壊的操作を伴う変更を適用する場合, the IaC 保守担当 shall 事前に既存挙動との等価性を検証する。
5. The `my-home-network` リポジトリ shall Terraform の構文検証が成功する状態を維持する。
6. The `my-home-network` リポジトリ shall Ansible の静的解析が成功する状態を、是正の完了時点で達成する。
7. The `gitops-apps` リポジトリ shall すべての Kustomize および Helm 定義が、依存を取得していないクローンからでもレンダリング可能である状態にする。
8. The 両リポジトリ shall 要件 12.5 から 12.7 の検証を自動で実行する仕組みを持つ。
9. When 静的解析が是正の完了前は失敗する場合, the IaC 保守担当 shall 当該検証の自動実行を、成功する状態に到達してから導入する。
10. If 是正の適用によって既存の稼働に影響が生じた場合, then the IaC 保守担当 shall 当該変更を切り戻せる状態を維持する。
11. The IaC 保守担当 shall 要件 12.10 における切り戻しの対象範囲を、マニフェストの復元とデータの復元に分けて定義する。
12. The IaC 保守担当 shall 是正を、リポジトリごとに独立してコミット可能な単位に分割する。
13. The IaC 保守担当 shall 高い影響度を持つ変更 (認証情報のローテーション、git 履歴の書き換え、Terraform の差分抑止の解除、ワークロードへのリソース制限の導入、カスタムリソース定義の削除) を、他の変更と分けて適用する。
14. The IaC 保守担当 shall 各段階の完了時点について、その時点で作業を停止した場合にシステムが整合した状態にあることを条件として定義し、当該時点で未是正のまま残る範囲を記録する。
15. The 設計 shall 停止を許可する点を段階の境界として定義し、各境界について停止した場合の整合条件を持つ。
16. If 段階の途中で停止せざるを得ない場合, then the IaC 保守担当 shall 不整合が残る箇所を記録し、再開時に最初にその解消を行う。
17. When 永続データまたは復元不能な資産を失う操作を実行しようとする場合, the IaC 保守担当 shall 事前に対象と影響範囲を運用者へ提示し、承認を得たうえで実行する。承認を得ずに当該操作を実行しない。

### Requirement 13: xrayvpn の稼働停止

**Objective:** ホームラボ管理者として、当面利用しない xrayvpn を、定義を失わずに停止したい。それにより、遊休ワークロードがリソースと攻撃面を占有する状態をなくしつつ、必要になったときに復帰できる。

#### Acceptance Criteria

1. The `xrayvpn` アプリケーション shall 稼働するコンテナを持たない状態にする。
2. The `gitops-apps` リポジトリ shall 停止後も `xrayvpn` の稼働構成を定義するマニフェストを保持し、復帰が設定値の変更のみで完了する状態にする。
3. The `vps_proxy` ロール shall xrayvpn 向けのバックエンド経路を無効化する。
4. While `xrayvpn` が停止している間, the ホームラボ shall 外部から到達可能でありながら応答しない経路を保持しない。
5. The IaC 保守担当 shall 復帰に必要な手順を、停止時に変更した設定値の一覧として記録する。
6. The `xrayvpn` の未適用マニフェストの削除 shall 要件 4.2 が定める削除に含め、停止対象の判断とは独立に実施する。本項は独立した是正を求めない。

### Requirement 14: クラスタ上の孤児リソースの除去

**Objective:** ホームラボ管理者として、クラスタ上で稼働するものと Git 上の定義が対応している状態にしたい。それにより、GitOps を導入していながら実態が Git から読み取れないという状態を解消できる。

#### Acceptance Criteria

1. The IaC 保守担当 shall クラスタ上のワークロードのうち、ArgoCD の管理下になく、かつ `gitops-apps` に対応する定義が存在しないものを列挙する。
2. The ホームラボ shall 起動に失敗し続けているワークロードを保持しない。
3. The ホームラボ shall 実行が完了した使い捨ての診断用 Pod を保持しない。
4. The ホームラボ shall 撤去済みとドキュメントに記録されている機構について、その実体 (コントローラ、カスタムリソース定義) をクラスタ上に保持しない。
5. When 孤児リソースを削除する場合, the IaC 保守担当 shall 削除前に永続データの有無を確認し、あわせて当該データの再構築元 (Git 上の定義、外部からの再取得、再生成) を特定して記録する。再構築元を特定できないものは削除の対象から外す。
6. If 孤児リソースが必要な機能を提供していると判明した場合, then the `gitops-apps` リポジトリ shall 当該リソースの定義を追加し、ArgoCD の管理下に置く。
7. The IaC 保守担当 shall 除去の完了後、クラスタ上のワークロードと Git 上の定義が対応することを確認する。
8. The バックアップの成果物を保持するオブジェクトストレージの永続ボリューム shall 「クラスタ内の永続データは復旧対象ではない」の例外として扱う。当該ボリュームは他のリソースの復旧手段であり、要件 10.7 の削除防御の対象に含める。

### Requirement 15: エッジホストの証明書供給の再建

**Objective:** ホームラボ管理者として、公開サイトが有効な証明書で配信され、その更新が自動で継続する状態にしたい。それにより、証明書の失効がサービス停止に直結する現状を解消できる。

#### Acceptance Criteria

1. The ホームラボ shall 公開しているホスト名に対して、有効期限内の証明書を提示する。
2. The エッジホスト shall 更新を要する証明書について更新を自動で継続し、いずれの供給機構による証明書も人手の介入なしに失効しない状態にする。
3. The IaC 保守担当 shall 証明書の供給をエッジホスト上で完結させ、他ホストからの配布に依存しない経路とする。更新を要する機構については、更新もエッジホスト上で自律的に完了する。
4. When 新しい証明書供給機構を確立した場合, the ホームラボ shall 各公開ホスト名に対する発行系を 1 つに定め、同一ホスト名に対して並走する既存の発行系を撤去する。
5. The `letsencrypt` ロール shall 到達不能な変数によって恒久的にスキップされる配布処理を保持しない。
6. The エッジホスト shall 更新を要する機構について、更新の失敗を検知できる状態にする。
7. The `my-home-network` リポジトリ shall 参照されない証明書配布関連の変数を保持しない。
8. When 証明書の供給を再建した場合, the IaC 保守担当 shall 公開ホスト名への外部からの接続が正常な応答を返すことを確認する。
9. The エッジホストの証明書供給 shall `fickledev.com` 系の配信をエッジホスト外へ移した後も、エッジホストが終端し続ける公開ホスト名すべてを対象に含める。要件 24 の移設は本要件を不要にしない。
10. When `fickledev.com` および `www.fickledev.com` の配信をエッジホスト外へ移した場合, the ホームラボ shall 当該 2 ホスト名について、オリジン証明書の失効を原因とする配信断が発生しない状態にする。
11. While Cloudflare のプロキシを経由して配信されるホスト名がエッジホスト上に存在する間, the エッジホスト shall 当該ホスト名に対して Cloudflare Origin CA が発行した証明書を提示する。本項は段階 0 から段階 3 までの橋渡しであり、要件 15.15 により当該ホスト名が存在しなくなった時点で機構ごと撤去する。
12. The エッジホスト shall Cloudflare のプロキシを経由しないホスト名、および Cloudflare の管理ゾーンに属さないホスト名に対して、公開的に信頼される証明書を ACME の DNS-01 検証によって取得する。
13. The IaC 保守担当 shall 各公開ホスト名について、いずれの機構が証明書を供給するかを一覧として記録する。
14. The `vps_proxy` ロール shall 証明書供給機構の設定をロールのテンプレートとして保持し、ロールの適用によって当該設定が失われない状態にする。
15. When 配信の移設によっていずれかの証明書供給機構を利用するホスト名が存在しなくなった場合, the IaC 保守担当 shall 当該機構の定義と生成物の双方を除去し、エッジホストの証明書供給を単一の機構に収束させる。

### Requirement 16: エッジホストの実機と定義の整合

**Objective:** ホームラボ管理者として、エッジホストの構成管理が実際に完走し、その結果が実機の状態と一致する状態にしたい。それにより、ロールを流すことが復旧手段として機能するようになる。

#### Acceptance Criteria

1. The `vps_proxy` ロール shall エッジホストに対して最後まで完走する。
2. The `vps_proxy` ロール shall 実機に存在しないパッケージを前提とするタスクを、前提の導入または当該タスクの除去により解消する。
3. If 実機にのみ存在し定義に存在しない設定がある場合, then the IaC 保守担当 shall ロールの適用によって当該設定が失われることを事前に確認し、失わせるか定義側に取り込むかを決定する。当該設定には現に外部からの接続を受けている公開経路が含まれるため、判定の対象を「稼働していない設定」に限定しない。
4. The `vps_proxy` ロール shall 参照されない変数と、対象が既に存在しない一度限りの移行処理を保持しない。
5. The `vps_proxy` ロール shall 到達不能なホストを上流として定義しない。
6. The エッジホスト shall ホスト自身にネットワークフィルタを持ち、上流のネットワーク制御のみに依存しない状態にする。
7. The エッジホスト shall 外部への公開が不要なサービスを、外部から到達可能なアドレスに待ち受けさせない。
8. The エッジホスト shall ログの保存容量に上限を持つ。
9. The エッジホスト shall 保留中のパッケージ更新を適用し、再起動を要する状態を解消する。
10. The エッジホスト shall 仮想化環境で意味を持たないサービスおよび失敗し続けるサービスを稼働させない。
11. The `vps_proxy` ロール shall 到達経路が存在しないアドレスへのフォールバック分岐を保持しない。
12. The 参照されない証明書バンドルの生成処理の削除 shall 要件 4.6 が定める削除に含める。本項は独立した是正を求めない。
13. The `vps_proxy` ロール shall 配信をエッジホスト外へ移したホスト名について、HTTP フロントの vhost 定義と対応する上流変数のいずれも保持しない。
14. The エッジホスト shall ネットワークフィルタの機構を単一に定める。ロールは現在 2 つの機構 (パケットフィルタのフロントエンドと、永続化された転送規則) を同時に配布しており、許可集合の情報源が分散している。
15. The エッジホストの許可ポート集合 shall 現に稼働している全ての公開経路を含む。TCP のみを列挙した一覧を情報源とせず、UDP で待ち受ける経路を欠落させない。
16. The `vps_proxy` ロール shall リバースプロキシとして不要な転送および送信元変換の設定を保持しない。
17. The IaC 保守担当 shall フィルタの実装に先立ち、外部から到達可能なポートの集合を確定する。測定済みの事実として、25 / 143 / 443 / 465 / 587 / 993 は接続が確立し、110 / 995 は RST が返り経路は開通したうえで待受が不在、22 はドロップされる。内向きの 25 番は提供元側の遮断が解除済みであり、後続のメール基盤の受信経路として利用できる。ホストのフィルタが停止している以上ホスト側で落とす経路がないため、22 の遮断は提供元側によるものと確定する。
18. The IaC 保守担当 shall 未測定の待受 (4190 および UDP 19132) について到達性を確定する。測定は発側の外向き 25 番が遮断されていない経路から行う。家庭回線からの測定は経路の発側で落ちるため、宛先側のフィルタの状態を判定する根拠にならない。UDP で待ち受ける経路は TCP による測定の対象としない。
19. The エッジホスト shall ホストファイアウォールが実際に稼働している状態にする。現在、当該機構は起動時有効の設定を持ちながら停止しており、定義側の許可リストは実機で一切効いていない。HAProxy が待ち受ける全ポートが素通しになっている。
20. When ホストファイアウォールを有効化する場合, the IaC 保守担当 shall 事前に対象と影響範囲を運用者へ提示し、承認を得たうえで実行する。有効化は管理経路を含む到達性を失わせうる操作であり、要件 12.17 の対象とする。
21. The IaC 保守担当 shall 有効化に先立ち、許可集合を確定する独立した作業項目を設ける。確定の入力は要件 16.17 が定める到達可能ポートの実測値と、現に稼働している公開経路とする。現行の許可リストは `25/80/143/443/465/587/993/4190` であり、SSH の 22 番と UDP 19132 のいずれも含まない。当該リストをそのまま適用しない。
22. When ホストファイアウォールを有効化する場合, the IaC 保守担当 shall 有効化の前に、管理経路 (tailnet のインタフェース、および必要な場合は SSH の待受ポート) が許可対象に含まれていることを、独立した検証項目として確認する。既定ポリシーとインタフェース指定の双方について確認する。
23. The 設計 shall ホストファイアウォールの有効化によって管理経路を失った場合の復旧手段が、本 spec の許可範囲外であることを制約として記録する。当該ホストの提供元コンソールおよび物理コンソールへの操作は本 spec の実行者が行えない。
24. The IaC 保守担当 shall 外部から到達する平文の IMAP の待受について、フィルタの許可対象に残すか閉じるかを決定し、判断と理由を記録する。現在 143 番は外部から接続が確立するが、背後のサービスは停止している。

### Requirement 17: 管理対象ホストへの到達性の回復

**Objective:** ホームラボ管理者として、インベントリに定義された全ホストへ、実行環境に依存せず構成管理が到達する状態にしたい。それにより、是正の結果を実機で検証でき、到達性が作業者の手元のファイル配置に左右されなくなる。

#### Acceptance Criteria

1. The IaC 保守担当 shall インベントリに定義された全ホストへ、公開鍵認証で接続できる状態にする。
2. The インベントリ shall 各ホストの接続ユーザーとして、当該ホストに実在するアカウントを与える。
3. The ホームラボ shall インベントリ上のホスト名とグループ名が衝突しない状態にする。
4. The インベントリ shall master と agent を判別可能なグループ構成にする。
5. The `argocd` playbook shall ArgoCD の導入対象を制御プレーンに限定する。
6. When 到達性を回復した場合, the IaC 保守担当 shall インベントリに定義された全ホストに対する疎通確認が成功することを確認する。
7. The IaC 保守担当 shall 接続用の公開鍵が認可済みでないホストへ、当該ホストを収容する仮想化基盤のノードから公開鍵を注入する。対象はコンテナ 2 件とする。
8. When 公開鍵を注入する場合, the IaC 保守担当 shall 収容元ノードからの操作で完結させ、仮想化基盤のコンソールへの直接操作を要しない手段で行う。
9. The IaC 保守担当 shall 接続に用いる秘密鍵をシークレット管理基盤に登録し、そこを単一の情報源として実行環境へ供給する。いずれの実行環境からも同一の鍵が供給される状態にする。リポジトリおよび作業ツリーに平文で保持しない。
10. The インベントリ shall 秘密鍵をファイルパスで参照しない。同一のパスが実行環境ごとに異なる鍵へ解決されうるため、パスによる指定は鍵の同一性を固定しない。
11. The Ansible 実装 shall 対象ホストの認可済み公開鍵を宣言的に定義し、繰り返し適用しても結果が変わらない形で適用する。対象は要件 17.7 が定めるコンテナ 2 件を含むインベントリ上の全ホストとし、定義に現れない既存の認可済み公開鍵の扱いを決定する。

### Requirement 18: 死蔵ストレージと孤児ディレクトリの解放

**Objective:** ホームラボ管理者として、使われていないストレージが確保されたままの状態を解消したい。それにより、容量を実際に必要とする用途へ回せる。

#### Acceptance Criteria

1. The ホームラボ shall 置換済みのオブジェクトストレージ向けに確保された領域を解放する。
2. When 領域を解放する場合, the IaC 保守担当 shall 実機のマウント、永続化設定、インベントリ変数、対応する playbook、仮想化基盤の定義における当該ボリュームの宣言、および仮想化基盤上でのディスクの切り離しとボリューム実体の削除を、いずれも欠かさず撤去する。ゲスト内のマウント解放と永続化設定の撤去のみでは領域の予約が返らない。
3. The ホームラボ shall 維持すると判断した領域について、その用途と判断を記録したうえで保持する。当該領域は、現に稼働しているファイル共有サービスの実データを Kubernetes 側へ移設するための移行先として確保済みであり、現時点で空であることを解放の根拠としない。
4. The ノード shall 対応する名前空間も永続ボリュームも存在しないローカルストレージのディレクトリを保持しない。
5. When ディレクトリを削除する場合, the IaC 保守担当 shall 削除前に対応するリソースが存在しないことを確認する。
6. When 領域を解放した場合, the IaC 保守担当 shall 解放によって利用可能になった容量を、対象のノード、対象のストレージ、および容量が判別できる形で記録し、後続の資源配分の判断材料として参照できる状態にする。記録の対象は削除したデータ量ではなく、予約の返却によって増加した空き容量とする。
7. When 撤去対象を特定する場合, the IaC 保守担当 shall 実行実績も参照元も持たない playbook と、現に他の用途で参照されている playbook を区別し、前者を削除し、後者については当該領域に対応するインベントリ変数のみを撤去する。
8. When 仮想化基盤の定義から追加ボリュームの宣言を除去する場合, the IaC 保守担当 shall 残るボリュームの割当先が変化しないことを適用前の計画で確認し、既存ボリュームの破棄と再作成を伴う計画を適用しない。
9. The 仮想マシン shall ゲスト内で解放された領域が下層のストレージへ返却される状態にする。
10. The 仮想化基盤の定義 shall 領域返却の設定を保持し、その変更が適用に反映される状態にする。本項は要件 4.7 が定める差分抑止の解除を前提とする。
11. The IaC 保守担当 shall 割当容量がゲスト内の実使用量を大きく上回るゲストを洗い出し、縮小するか現状を維持するかの方針をゲストごとに決定し、判断と理由を記録する。本項は縮小の実施そのものを求めない。

### Requirement 19: 定期実行とバックアップ設定の是正

**Objective:** ホームラボ管理者として、定期実行が意図した頻度で動き、その成果物が無制限に増えない状態にしたい。それにより、誤設定が資源を消費し続ける状態を解消できる。

#### Acceptance Criteria

1. The バックアップのスケジュール定義 shall 実行基盤が解釈するフィールド数に一致する記法で記述する。
2. The バックアップのスケジュール定義 shall 意図した頻度で実行される。
3. The バックアップ設定 shall 保持世代の上限を持ち、成果物が無制限に増加しない状態にする。
4. The IaC 保守担当 shall 誤った頻度により蓄積された成果物を除去する。
5. The バックアップ設定 shall 提供元で廃止予定と告知されている方式への依存を解消するか、廃止時期と移行方針を記録する。
6. The IaC 保守担当 shall 保存先ストレージが無効化されていることによりバックアップが起動のたびに失敗している状態を解消し、当該ストレージが有効であることを構成管理の定義から冪等に保証できる状態にする。
7. The 完了する処理 shall 実行後に自動で除去される設定を持つ。
8. The エッジホスト shall 構成管理の対象外で定期実行される処理を保持しない。
9. The バックアップの構成 shall バックアップジョブの定義、スケジュール、保持世代を構成管理の定義から冪等に構築できる状態にする。
10. The バックアップ機構 shall 必要とするシークレットを、シークレット管理基盤を単一の情報源として受け取る。
11. The IaC 保守担当 shall 既存のバックアップジョブ定義および蓄積された成果物を保全の対象とせず、バックアップの構成を定義から作り直す。
12. When バックアップの構成を構築した場合, the IaC 保守担当 shall 設定が投入されたことではなく、バックアップが完了し復元可能な成果物が保存先データストア上に 1 件以上存在することをもって完了とする。
13. The バックアップ機構 shall 失敗の原因を特定できる状態にする。エラー応答の扱いは要件 8.6 が定める方針に従う。
14. When 不可逆な削除を伴う是正を適用する場合, the IaC 保守担当 shall 事前に要件 19.12 の完了条件が満たされていることを確認する。
15. The バックアップの構成 shall 保存先を、保護対象のゲストが載る物理ディスクと異なる物理ディスク上に置く。単一のディスクの障害によって保護対象と成果物の双方を同時に失う構成を採らない。
16. The バックアップ対象の一覧 shall 単一の情報源から導出される状態にする。情報源を構成管理のインベントリとし、実行基盤側のジョブ定義がインベントリと異なる対象集合を持つ状態を解消する。
17. The バックアップ設定 shall 保護を要しないボリュームを対象から除外する。除外の意図はインベントリ上の宣言を情報源とし、実行基盤側の各ディスクのバックアップ対象指定へ反映する。
18. The IaC 保守担当 shall 要件 19.15 の分離が既に成立していることを確認し、記録する。保護対象 7 件のルートディスクは各ノードの `pve/data` (sda) にあり、バックアップのデータストアは hp-z440 の sdc 上にある。ディスク単体の故障では保護対象と成果物のいずれかが残る。残存リスクはディスク単位ではなくホスト単位にあり、hp-z440 の全損時に当該ノード上の元データと成果物を同時に失う。この粒度でリスクを記録する。
19. When 不可逆な削除を行う対象がバックアップのデータストアと同一の物理ディスク上にある場合, the IaC 保守担当 shall 削除の直前に当該ボリュームの実データの複製を別の物理ディスク上へ取得する。退避先の所要容量は予約済み容量ではなく実データ量を基準とする。
20. The バックアップ対象の一覧 shall 後続のメール基盤のメールボックスを保持する永続ボリュームが載るノードを含む。受信したメールは再構築できず、当該ボリュームは冗長性を持たない単発ディスク上に置かれるため、保護の対象から外さない。

### Requirement 20: シークレット供給の棚卸しと管理外認証情報の収容

**Objective:** ホームラボ管理者として、シークレット管理基盤の内容と実際の参照が一致し、管理外の場所に認証情報が平文で存在しない状態にしたい。それにより、棚卸しの対象が把握可能になる。

#### Acceptance Criteria

1. The IaC 保守担当 shall シークレット管理基盤に登録されたキーのうち、どこからも参照されないものを特定し、削除するか保持理由を記録する。
2. The シークレット管理基盤 shall 廃止済みの機構のための復号鍵を保持しない。
3. The シークレット管理基盤 shall 同一の値に対して紛らわしい重複キーを保持しない。
4. The IaC 保守担当 shall コードが参照するがシークレット管理基盤に存在しないキーを特定し、対応表の記述を実態に一致させる。
5. The エッジホスト shall 定期実行される処理の中に認証情報を平文で保持しない。
6. When 認証情報を平文の定期実行定義から移す場合, the IaC 保守担当 shall 当該処理を構成管理の対象とし、値をシークレット管理基盤から供給する。
7. If 当該認証情報がローテーション不可能である場合, then the IaC 保守担当 shall ローテーション不可の理由と残存リスクを記録する。

### Requirement 21: 重複した制御機構と未使用資産の解消

**Objective:** ホームラボ管理者として、同一の対象を制御する機構が 1 つだけ存在する状態にしたい。それにより、どちらが有効なのか判断する必要をなくせる。

#### Acceptance Criteria

1. The クラスタ shall 同一の生成対象を持つアプリケーション生成定義を重複して保持しない。
2. If 生成定義が恒久的に失敗し続けている場合, then the IaC 保守担当 shall 当該定義を除去する。
3. The クラスタ shall 同一のコンポーネントを 2 つの導入経路で管理しない。
4. The 証明書の複製設定 shall 複製先を実際に必要とする名前空間に限定する。
5. The クラスタ shall 実在しない転送設定を参照する公開定義を保持しない。
6. The クラスタ shall どこからも参照されない転送設定を保持しない。
7. The クラスタ shall 初期導入時にのみ必要な認証情報を、導入完了後に保持しない。
8. The クラスタ shall 廃止済みの機構のための設定を保持しない。
9. The クラスタ shall 既定のものと機能が同一で利用者のいないストレージ定義を保持しない。
10. The クラスタ shall 中身を持たない名前空間を保持しない。
11. The クラスタ shall インスタンスを持たないカスタムリソース定義について、保持するか除去するかを判断し記録する。
12. The 各ワークロード shall 保持する履歴の世代数に上限を持つ。
13. The クラスタ shall 同一のリポジトリの同一パスを走査するアプリケーション生成定義を 2 つ保持しない。両リポジトリに同一内容の定義が存在し、いずれもクラスタ上で稼働している。
14. The 管理ゾーン shall 発行済みの検証用レコードのうち、対応する発行系を失ったものを保持しない。Terraform の管理対象外として宣言された種別についても、除去の担当を定めないまま残さない。

### Requirement 22: 静的品質ゲートの拡張

**Objective:** ホームラボ管理者として、記述の揺れと検査されないコードをなくしたい。それにより、レビューが本質的な内容に集中できる。

#### Acceptance Criteria

1. The 両リポジトリ shall YAML の静的検査を、上流由来の配布物とテンプレート言語を含むファイルを除外したうえで実行する。
2. The 両リポジトリ shall 改行コードを統一する。
3. The `my-home-network` リポジトリ shall スクリプトのテストが実際に実行される状態にする。
4. The `my-home-network` リポジトリ shall スクリプトの静的検査と整形の設定を持つ。
5. The Terraform 設定 shall provider のバージョンに上限を設定する。
6. The `my-home-network` リポジトリ shall 変数定義ファイルの追跡除外を、拡張子の派生形も含めて設定する。
7. The `my-home-network` リポジトリ shall 依存関係の脆弱性通知を有効にする。
8. The `my-home-network` リポジトリ shall 既定ブランチへの直接変更に対する保護を設定する。
9. The `my-home-network` リポジトリ shall 利用条件を明示する。

### Requirement 23: リポジトリ資産の整理

**Objective:** ホームラボ管理者として、放置された枝と空のリポジトリが残らない状態にしたい。それにより、どれが現行かを判断する必要をなくせる。

#### Acceptance Criteria

1. The `gitops-apps` リポジトリ shall 既定ブランチから大きく乖離したまま放置された枝を、内容を確認したうえで除去する。
2. The IaC 保守担当 shall 内容を持たないリポジトリを除去する。
3. The `gitops-apps` リポジトリ shall 依存チャートの取得物と固定情報の追跡方針を明示し、追跡除外の設定に反映する。
4. The `gitops-apps` リポジトリ shall 誤った位置に配置された自動実行の定義を、正しい位置へ移すか除去する。
5. The IaC 保守担当 shall 本 spec の成果物を、段階 3 の完了後に追跡対象に含める。
6. The `gitops-apps` リポジトリ shall 履歴に含まれる平文のシークレット定義について、非公開である前提を記録したうえで、除去の要否を判断する。

### Requirement 24: portfolio の Cloudflare Workers への移設

**Objective:** ホームラボ管理者として、公開サイト `fickledev.com` の配信を自宅とエッジホストに依存しない基盤へ移したい。それにより、オリジン証明書の失効・LXC の停止・VPS の障害がそのままサイト停止になる構造を解消できる。

#### Acceptance Criteria

1. The `portfolio` リポジトリ shall アプリケーションを静的エクスポートとしてビルドし、画像の配信が実行時の最適化処理に依存しない状態にする。
2. When 問い合わせフォームが送信された場合, the Worker shall 人間性検証トークンの検証と通知先への送信を行い、成功時および失敗時の応答が移設前と等価であることを保つ。
3. The `portfolio` リポジトリ shall 静的エクスポートと両立しない実行時経路 (API ルート、Server Action) をアプリケーション側に保持しない。
4. The `portfolio` リポジトリ shall Server Action として使用されていない検証関数の実装と、それを有効化する実験的設定を保持しない。
5. The `portfolio` リポジトリ shall 静的成果物の配信と動的経路の振り分けを、実行基盤の設定ファイルとして宣言する。
6. The Worker shall 人間性検証の秘密鍵と通知先の URL を、リポジトリおよびビルド成果物に平文で含まない形で受け取る。
7. The IaC 保守担当 shall 前項の 2 値をシークレット管理基盤に登録し、そこを単一の情報源として実行基盤へ供給する。
8. The 自動デプロイ shall ビルド成果物と Worker を実行基盤へ直接配信する方式に置き換える。
9. The 自動デプロイ shall コンテナイメージの転送、SSH 秘密鍵、および VPN の認証鍵を必要としない。
10. The `my-home-network` リポジトリ shall `fickledev.com` および `www.fickledev.com` の配信先を Terraform の定義として保持し、実行基盤のカスタムドメインとして宣言する。
11. When 配信先を実行基盤のカスタムドメインとして宣言する場合, the Terraform 設定 shall 同一ホスト名に対するエッジホスト宛のアドレスレコードを同時に保持しない。
12. The `vps_proxy` ロール shall `fickledev.com` および `www.fickledev.com` の HTTP フロント設定と、その配信先を指す上流変数を保持しない。
13. The `vps_proxy` ロール shall 到達不能な上流を指す `/blog` の経路定義と、対応する上流変数を保持しない。
14. When 上流変数を削除する場合, the `vps_proxy` ロール shall 当該変数を必須とする前提条件チェックからも同時に除去し、ロールが完走する状態を保つ。
15. The ホームラボ shall 移設後、旧配信元の LXC を停止し除去する。当該 LXC は `hp-z440` 上の LXC 115 (`portfolio`、`192.168.1.103`、rootfs 32G) であり、Terraform の管理対象に存在しないため、除去は基盤側の操作として実施する。
16. When 旧配信元の LXC を除去する場合, the IaC 保守担当 shall 除去前に永続データの有無を確認し、保全または破棄の判断を記録する。
17. When 移設が完了した場合, the ホームラボ shall `https://fickledev.com` および `https://www.fickledev.com` への外部からの要求に対して正常な応答を返す。
18. The IaC 保守担当 shall 移設の切り戻し手段を、配信先をエッジホストへ戻す手順として記録し、戻すために必要な定義が失われない状態にする。
19. The `portfolio` リポジトリ shall スタイルの生成対象にアプリケーションのディレクトリを含め、レイアウトに記述されたクラスが成果物に含まれる状態にする。
20. The `portfolio` リポジトリ shall ホスト鍵の検証を無効にしたまま外部ホストへ接続する自動処理を保持しない。
21. The `portfolio` リポジトリ shall 配信構成とデプロイ手順を記述したドキュメントを持ち、その記述が静的エクスポートと Worker による配信、実行基盤への直接配信の手順、およびシークレットの供給元と一致する状態にする。

### Requirement 25: authentik と LDAP クライアント設定の撤去

**Objective:** ホームラボ管理者として、既存の認証基盤とそのクライアント設定を痕跡なく撤去したい。それにより、既定のまま外部公開されている管理者認証情報を排除し、Kanidm による認証基盤を単一の認証経路として構築する前提を整えられる。

#### Acceptance Criteria

1. The `gitops-apps` リポジトリ shall `apps/authentik-fickledev/` 配下のすべてのファイルを削除する。
2. The `gitops-apps` リポジトリ shall 当該基盤専用として定義され、かつ接続する利用者を持たない PostgreSQL クラスタの定義と、その定期バックアップの定義を削除する。
3. The `gitops-apps` リポジトリ shall 共有 PostgreSQL クラスタの bootstrap 定義から、当該基盤向けのデータベースおよびロールの宣言を除去する。
4. When 当該基盤のマニフェストを削除する場合, the IaC 保守担当 shall 削除前にクラスタ上の関連リソースを列挙し、永続データを持つものについて保全または破棄の判断を記録する。当該チャートは永続ボリューム要求を持たない。
5. While ApplicationSet の syncPolicy が `prune: true` かつ `selfHeal: true` である間, when 当該基盤の Application 生成元ディレクトリが削除された場合, the IaC 保守担当 shall クラスタ上の名前空間およびリソースが削除される挙動を前提として作業手順を組む。
6. The IaC 保守担当 shall 既定の名前空間に存在する ArgoCD 管理外の重複した認証基盤のワークロードを除去する。当該除去は要件 14 が定める孤児リソースの除去と同一の対象であり、重複して実施しない。
7. The Terraform 設定 shall 当該基盤へ向けたトンネルの公開ホスト名ルートと、対応する DNS レコードを削除する。
8. The `my-home-network` リポジトリ shall `sssd` ロール一式、対応する playbook、およびインベントリが保持する bind 用の認証情報変数を削除する。
9. The IaC 保守担当 shall シークレット管理基盤から当該基盤向けのキーを削除し、対応する同期定義をマニフェストから除去する。
10. The 両リポジトリ shall README、steering、および開発支援用の指示ファイルから当該基盤への言及を除去し、認証基盤の現状を記載する。
11. If 撤去後に残存するリソースがクラスタ上に確認された場合, then the IaC 保守担当 shall 当該リソースを手動で除去し、除去内容を記録する。

### Requirement 26: 認証基盤の構築とサービス統合

**Objective:** ホームラボ管理者として、単一の認証基盤で各サービスと NAS のログインを扱いたい。それにより、サービスごとに独立した認証情報を持つ状態と、POSIX アカウントを手作業で整合させる状態を解消できる。

#### Acceptance Criteria

1. The ホームラボ shall 認証基盤を k3s 上に構築し、その状態を保持する永続ボリュームを持つ。
2. The 認証基盤 shall TLS を自身で終端する。リバースプロキシを前段に置く場合も終端を省略せず、StartTLS に依存する経路を持たない。
3. The Terraform 設定 shall 認証基盤の公開ホスト名を新規に定義し、DNS レコードと公開経路を管理対象として保持する。
4. The 認証基盤 shall オンラインバックアップを有効にし、バックアップの対象と保存先を定義として明示する。
5. When バックアップから復元する場合, the IaC 保守担当 shall 復元がバックアップ取得時と同一のバージョンでのみ成立することを前提とした手順を持つ。
6. The `gitops-apps` リポジトリ shall 認証基盤のコンテナイメージを可変でない参照で指定し、マイナーバージョンを飛ばした更新が自動同期によって適用されない状態にする。
7. The `gitops-apps` リポジトリ shall 認証基盤のユーザー、グループ、および OIDC クライアントを宣言的に定義し、繰り返し適用しても結果が変わらない手段で適用する。
8. The IaC 保守担当 shall 手動の画面操作によってのみ存在する定義を認証基盤上に保持しない。
9. The 設計 shall 宣言的な適用手段が上流の公式提供物ではない事実を記録し、供給元とバージョンを固定する。
10. The NAS shall 認証基盤のクライアントと POSIX 解決デーモンを導入し、その供給元を apt のパッケージソースとして構成管理の定義に持つ。
11. The NAS shall 利用者のホームディレクトリを自動生成する。生成先の接頭辞、参照する属性、別名、命名方式、雛形の使用有無、およびネットワークマウントの接頭辞を設定として保持する。
12. The NAS shall ログインを許可するグループをホスト単位で制限する。
13. The NAS shall ローカルのグループのメンバを、認証基盤側のグループによって拡張する。
14. When UID および GID の割当レンジを決定する場合, the IaC 保守担当 shall 事前に実機上の既存ファイルの所有者と UID/GID を確認し、その結果に基づいてレンジを決定する。
15. If 既存の UID/GID と決定したレンジが整合しない場合, then the IaC 保守担当 shall 移行の要否と手順を判断し、記録する。
16. While NAS 上でのパスワード変更コマンドが認証基盤へ反映されない間, the ホームラボ shall 利用者が自身の認証情報を変更する経路を、認証基盤の画面またはクライアントコマンドとして提示する。
17. The 認証基盤 shall パスワードの再設定と 2 段階認証の登録を、メール送信基盤に依存せずに完結させる。
18. The Gitea shall 認証基盤と OIDC で連携する。当該設定は設定ファイルではなくデータベース上の認証ソースとして保持される事実を前提とする。
19. The `gitea` ロール shall 認証ソースの登録を、既存の一覧を取得して有無を判定し、作成と更新に分岐する形で適用する。冪等性を Gitea 側に依存しない。
20. The ArgoCD shall 認証基盤と OIDC で直接連携する。中継する認証コンポーネントを導入しない。
21. The `gitops-apps` リポジトリ shall ArgoCD の CLI 用に、PKCE を要求する公開クライアントを別途登録する。
22. The ArgoCD shall RBAC のポリシーにグループ名でロールを対応付ける。グループ名の大文字小文字を認証基盤側の定義と一致させる。
23. The Home Assistant および Garage の UI shall Ingress の forward auth により保護される。
24. The Garage の S3 API のパス shall forward auth の適用対象に含まれない。
25. The Home Assistant shall 内蔵の認証を保持したまま forward auth の背後に置かれ、転送元アドレスの解釈と信頼するプロキシを設定として持つ。
26. The Home Assistant shall コンパニオンアプリが用いる経路について、forward auth の適用除外を定義として持つ。
27. The Guacamole shall 認証をヘッダ認証の拡張と forward auth の組み合わせで行う。内蔵の OIDC 拡張は implicit flow のみを実装し認証基盤がこれを拒否するため、使用しない。
28. The forward auth の経路 shall 上流から到達する利用者識別ヘッダを、認証の判定より前に除去する。
29. When Guacamole の認証を認証基盤へ移した場合, the IaC 保守担当 shall `console.fickledev.com` に対する Cloudflare Access のアプリケーション定義およびポリシーについて、撤去するか多層防御として保持するかを決定し、決定に従って Terraform の定義を更新する。
30. The `gitops-apps` リポジトリ shall forward auth の実現手段を単一に定め、対応する middleware を共通の middleware 定義に追加する。
31. The `gitops-apps` リポジトリ shall 既存の接続元アドレス制限の middleware を保持し、forward auth と連鎖させて適用する。
32. The 認証基盤 shall 開発基盤向けに 2 つの独立した OIDC クライアントを宣言として保持する。一方は開発環境そのものへの到達を、他方は開発環境が公開するサービスへの到達を制御する。
33. The 2 つの OIDC クライアント shall 許可するグループ、要求する認証情報の種別、およびセッションの有効期限を、相互に独立して設定できる。
34. The Gitea および ArgoCD shall OIDC のリダイレクト先として成立する HTTPS の公開オリジンを持つ。Gitea は現在 TLS 終端を持たない平文の経路のみで公開されており、ArgoCD の公開ホスト名は管理ゾーンに存在しない。本項は要件 26.18、26.20、26.21 の前提であり、それらに先行して満たす。
35. The `gitops-apps` リポジトリ shall forward auth の判定を担うワークロードを、アプリケーションとして構築する。認証基盤は OIDC のみを提供し forward auth の終端を提供しないため、middleware の転送先となる実体を別途要する。
36. The 認証基盤の OIDC クライアントの宣言 shall 前項のワークロード向けのクライアントを含む。後から定義を追加する際に同じ固定を再確認する手間が生じるため、最初の宣言に含める。
37. The 認証基盤 shall LDAPS の待受を有効にし、tailnet 上の他ホストから到達可能な経路を持つ。当該インタフェースは read-only であり、POSIX 統合の経路としては用いない。用途は外部のサービスによる認証の委譲に限る。
38. The 認証基盤 shall 利用者ごとにアプリケーション単位の認証情報を発行できる状態にする。LDAPS による bind は当該認証情報を用い、利用者の主たる認証情報を外部のサービスへ渡さない。

### Requirement 27: Kubernetes Dashboard の撤去

**Objective:** ホームラボ管理者として、Kubernetes Dashboard を撤去し、クラスタの管理操作の手段を kubeconfig と端末クライアントに一本化したい。それにより、外部公開経路と管理者権限のサービスアカウントを同時に手放せる。

#### Acceptance Criteria

1. The `gitops-apps` リポジトリ shall `apps/kubernetes-dashboard/` 配下のすべてのファイルを削除する。
2. The IaC 保守担当 shall 当該アプリケーション向けの公開経路の定義が Terraform 設定および管理ゾーンのいずれにも存在しないことを確認し、存在する場合は削除する。
3. The 両リポジトリ shall クラスタの管理操作の手段を kubeconfig と端末クライアントとして記述し、README および steering の記述をこれに一致させる。当該記述の対象はクラスタの管理操作に限り、ブラウザから提供される開発ワークスペースを含めない。
4. The `gitops-apps` リポジトリ shall 撤去をもって、バックエンドへの TLS 検証のスキップ、Kustomize に登録されない公開定義の二重定義、保守が終了したバージョンのコンテナイメージ、および実装と乖離した README の 4 点を同時に解消し、これらに対する個別の是正を行わない。
5. While ApplicationSet の syncPolicy が `prune: true` かつ `selfHeal: true` である間, when 当該アプリケーションの生成元ディレクトリが削除された場合, the IaC 保守担当 shall クラスタ上の名前空間およびリソースが削除される挙動を前提として作業手順を組む。
6. If 撤去後に残存するリソース (名前空間、サービスアカウント、クラスタロールの割り当て) が確認された場合, then the IaC 保守担当 shall 当該リソースを手動で除去し、除去内容を記録する。

### Requirement 28: 仮想化基盤上のゲストと定義の整合

**Objective:** ホームラボ管理者として、仮想化基盤の上で稼働しているゲストと Terraform の定義の対応が付いている状態にしたい。それにより、定義に現れないゲストが把握されないまま増え続ける状態を解消できる。

#### Acceptance Criteria

1. The IaC 保守担当 shall 仮想化基盤の各ノード上に存在するゲストを列挙し、Terraform の定義に対応するものと対応しないものを区別した一覧として記録する。
2. The IaC 保守担当 shall 定義に対応しないゲストについて、定義側に取り込むか管理対象外として扱うかを、ゲストごとに決定する。
3. When ゲストを管理対象外と決定した場合, the IaC 保守担当 shall その判断と理由を記録し、以後の照合において管理対象外であることを識別可能にする。
4. The IaC 保守担当 shall 停止したまま保持されているテンプレートおよび仮想マシンについて、保持するか除去するかを個別に決定し、決定を記録する。
5. The IaC 保守担当 shall 対応する実体を失った命名を持つディスクを洗い出し、記録する。
6. The IaC 保守担当 shall 本要件に基づいて稼働中のゲストを停止または除去しない。要件 24.15 が定める旧配信元のコンテナはこの限りでない。
7. The IaC 保守担当 shall 定義に対応しないゲストのうち、冗長性を持たない物理ディスクを直接占有し、かつバックアップの対象にも含まれていないものについて、要件 28.2 の決定にあわせて当該データの保全方針を決定し、判断と理由を記録する。

### Requirement 29: クラスタ内の証明書発行系のシークレット供給

**Objective:** ホームラボ管理者として、クラスタ内の証明書発行系が必要とするシークレットの供給元が定義から辿れる状態にしたい。それにより、クラスタ上の全 TLS が、誰も管理していない手動投入の値に依存する状態を解消できる。

#### Acceptance Criteria

1. The `gitops-apps` リポジトリ shall クラスタ内の ACME 発行者が参照するシークレットについて、その供給定義を保持する。当該シークレットは現在いずれのリポジトリにも定義を持たず、手動で投入された実体のみが存在する。
2. The 当該シークレットの供給 shall シークレット管理基盤を単一の情報源とする。要件 20.4 の棚卸しの対象に、コードが参照するがシークレット管理基盤に存在しないキーとして含める。
3. The IaC 保守担当 shall 当該発行者が発行する証明書の利用範囲を特定し、供給が途絶えた場合に影響を受けるアプリケーションを記録する。
4. When 供給定義を新設した場合, the IaC 保守担当 shall 既存の証明書が再発行されずに継続すること、および更新期日の到来時に発行が成功することを確認する。
5. The `cluster-issuer` アプリケーション shall 当該シークレットが存在しない状態で同期された場合に、その事実が同期の状態から判別できるようにする。
