# Implementation Plan

適用は design.md の Migration Strategy が定める段階に従う。タスク番号の並びと段階の対応は以下のとおり。

- 段階 0: タスク 1
- 段階 1: タスク 3 → タスク 4
- 段階 2: タスク 5
- 段階 3: タスク 6 → タスク 8
- 段階 4: タスク 7、タスク 9
- タスク 2 と タスク 10 は全段階に横断する。タスク 2 は認証情報が発生した段階でその都度適用し、タスク 10 は全段階の完了後に実施する

保全 (タスク 8) を段階 3 に置き、MX の公開 (タスク 7.1) を段階 4 に置くのは、外部からの受信が始まる前に保全を成立させるためである。MX の公開以降に到着したメールは再構築できない。

本 spec は `iac-hygiene-remediation` の完了を前提とする。とくに認証基盤の稼働 (同要件 26)、エッジホストの証明書供給 (同要件 15)、シークレットの Infisical への集約 (同要件 20) が成立していることを前提に置く。**LDAPS の待受と公開経路は当該 spec の範囲外**であり (要件 26 は LDAP を前提とする統合方式を採らない)、タスク 4.1 が本 spec の責務として構成する。

タスク 1.1 の 25 番ポートは提供元側で遮断されていたが解除済みである。到達が確認できるまで後続に進まない。タスク 1.4 の実証が成立しない場合、以降のタスクに着手しない。認証基盤の選定を見直す判断は本 spec の範囲外とし、結果の提示までを行う。

`(P)` は直前の同階層タスクと並行実行できることを示す。段階をまたぐ並行実行は行わない。作業の停止は段階の境界でのみ行う。

- [ ] 1. 環境側の前提を実測し、依存する機構を実証する

- [x] 1.1 受信ポートの到達を確認し資源を実測する
  - 外部から VPS への 25 番ポートが到達することを確認する。当該ポートは提供元側のフィルタで遮断されていたが解除済みであり、本項は解除状態が維持されていることの確認である
  - 確認を、OP25B の影響を受けない経路からの接続によって行う。VPS 上の待受状態の確認をもって到達の確認としない。家庭回線を経由する測定は外向き 25 番が遮断されているため無効であり、用いない
  - 用いた測定経路を結果とともに記録する。無効な経路で得た結果を後から判別できる形で残す
  - 到達が確認できない場合、提供元のコントロールパネルで再解除を行い、完了を確認するまで後続のタスクに着手しない。当該操作がコードによる管理の対象外であることを記録する
  - submission と IMAPS に用いる 465 / 587 / 993 番ポートは到達が確認済みであり、提供元側の操作を要しないことを記録する
  - VPS の利用可能メモリと swap を実測し、ウイルス検査機構が定義データベースの常駐に要する容量と突き合わせた結果を記録する。下回る場合、当該機構を有効化しない判断と残存リスクを記録する
  - _Requirements: 1.9, 1.10, 1.11, 1.12, 1.13, 1.15, 11.6_
  - _Boundary: FeasibilityProof_

- [x] 1.2 アプリケーションパスワードによる bind の成立を確認する
  - 認証基盤とメールサーバを最小構成で起動する。VPS および k3s の実環境を用いない
  - 対象とする認証基盤の版がアプリケーションパスワードの管理手段を備えることを確認する。あわせて当該版を `iac-hygiene-remediation` が固定した版と一致させる。一致しない版で得た結果を成立の根拠としない
  - メール用のアプリケーション定義と利用者グループを作り、利用者にアプリケーションパスワードを発行する
  - アプリケーション指定を含む bind DN での認証が成立することを、bind のみを行う操作によって確認する
  - 対照として、アプリケーション指定を含まない bind DN で同一の資格情報が拒否されること、利用者グループから除外した場合に bind が成立しないこと、および主クレデンシャルでは成立しないことを確認する
  - 実証環境の外に構成変更を及ぼしていないことを確認する
  - _Requirements: 1.1, 1.2, 1.7, 1.14, 2.1_
  - _Boundary: FeasibilityProof_
  - _Depends: 1.1_

- [x] 1.3 設定上書き経路と取得の成立を確認する
  - メールサーバの設定上書き経路に bind DN のテンプレート指定を置き、実行中の設定値を出力する操作で反映を確認する
  - 認証と利用者情報の項目定義を差し替え、既定の定義が参照する属性による失敗が解消することを確認する
  - アプリケーションパスワードによる取得のログインが成立することを確認する
  - 成立した上書き経路と、その経路で反映された設定値が記録として残る
  - _Requirements: 1.3, 1.4, 4.8, 4.9_
  - _Boundary: FeasibilityProof_
  - _Depends: 1.2_

- [x] 1.4 実証の結果を記録し着手を判断する
  - 成立した項目と成立しなかった項目を分けて記録する。環境側の実測値と測定経路を含める
  - 成立しなかった項目について、確認に用いた操作と得られた応答をそのまま残す
  - bind または取得のいずれかが成立しない場合、以降のタスクに着手せず、判断材料として結果を提示する。不成立の原因が認証基盤の版に起因するか機構そのものに起因するかを区別し、前者は版の更新を、後者は選定の見直しを提示する
  - 最小構成では再現されない条件を、本番構成で確認する項目として定める。認証局が発行した証明書による接続、クラスタ上で稼働する認証基盤への接続、および tailnet を経由する経路を対象とする
  - 着手の可否が判断できる形で結果がまとまっている
  - _Requirements: 1.5, 1.6, 1.8_
  - _Boundary: FeasibilityProof_
  - _Depends: 1.3_

- [ ] 2. 認証情報を単一の情報源から供給する

- [x] 2.1 キー空間を定義し供給経路を構成する
  - メール基盤が用いる認証情報のキー空間をシークレット管理基盤上に定義する。検索用のトークン、署名の秘密鍵、およびその他の認証情報を対象とする
  - k3s 側へは Operator 経由、VPS 側へは実行時の取得として供給する経路を構成する。いずれも `iac-hygiene-remediation` が確立した経路に従い、別の経路を導入しない
  - 署名の鍵について、秘密鍵側がシークレット管理基盤に登録され、公開鍵側のみが DNS の定義に現れる状態にする
  - リポジトリ全体の走査でメール基盤の認証情報が検出されない
  - _Requirements: 7.1, 7.2, 7.3, 7.5_
  - _Boundary: MailSecretSupply_

- [x] 2.2 認証情報の発行と充足検査を構成する
  - 新しい認証情報をローカルで生成し、シークレット管理基盤へ登録したうえで供給する手順を構成に組み込む
  - 認証情報が存在しない場合に適用を中止し、不足している値を示す検査を置く。適用の途中で停止させない
  - 値を欠いた状態で適用を試み、開始前に停止して不足している値が示されることを確認する
  - _Requirements: 7.4, 7.6_
  - _Boundary: MailSecretSupply_
  - _Depends: 2.1_

- [ ] 3. 認証基盤上のメール認証を構成する

- [x] 3.1 アプリケーション定義と利用者グループを宣言する
  - メール用のアプリケーション定義と利用者グループを宣言として保持し、両者を関連付ける
  - 当該グループに所属しない利用者がアプリケーションパスワードを発行できない状態にする
  - 利用者自身がアプリケーションパスワードを発行および失効できる状態を保つ
  - メール利用者グループに、メールクライアントが用いる資格情報の種別を許容するアカウントポリシーを与える。既定のポリシーは多要素を要求し、パスワードのみの資格情報を確定できない
  - 宣言を 2 回適用して 2 回目に変更が報告されない
  - 利用者をグループから除外した場合に、当該利用者のメール認証が成立しなくなることを確認する
  - _Requirements: 2.2, 2.3, 2.9, 2.10, 2.12, 8.5_
  - _Boundary: MailAuthProvisioning_
  - _Depends: 1.4_

- [x] 3.2 検索用サービスアカウントと命名規約を構成する
  - メール属性の読み取りを許可されたサービスアカウントを宣言として保持する。属性は検索結果の取得だけでなく検索条件として用いる場合にも読み取り許可を要する
  - 利用者のアカウント名をメールアドレスのローカル部と一致させる規約を宣言に反映する
  - メール属性を条件とする検索を、インデックスされた属性との論理積として組み立てる。当該属性のみを条件とする検索は資源制限により拒否される
  - 当該サービスアカウントの資格情報で論理積による検索が成立することを確認する
  - 読み取り許可を外した状態で同じ検索が 0 件を返すことを確認し、許可の欠落がエラーではなく空の結果として現れることを記録する。この確認を独立した手順として残す
  - _Requirements: 2.6, 2.8, 2.11_
  - _Boundary: MailAuthProvisioning_
  - _Depends: 3.1_

- [x] 3.3 POSIX パスワードによる bind を無効化する
  - 認証基盤の設定で、POSIX パスワードによる LDAP bind を無効化する
  - アプリケーション定義の適用が完了した後に実施する。先に無効化すると認証経路が一時的に存在しない状態になる
  - 無効化後、アプリケーション指定を含む bind のみが成立し、指定を含まない bind が成立しないことを確認する
  - _Requirements: 2.5_
  - _Boundary: MailAuthProvisioning_
  - _Depends: 3.2_

- [ ] 4. LDAPS の公開経路を確立する

- [x] 4.1 (P) LDAPS を tailnet から到達可能にする
  - 認証基盤の LDAPS の待受を有効にする
  - 待受を TLS を終端しない経路でクラスタ外へ公開する。HTTP を前提とする公開経路を用いない
  - tailnet からの接続のみを受け付ける状態にする
  - tailnet 上の別ホストから当該待受へ TCP 接続が成立する
  - _Requirements: 3.1, 3.2_
  - _Boundary: LdapExposure_
  - _Depends: 1.4_

- [x] 4.2 接続先ホスト名の解決を tailnet へ向ける
  - 認証基盤が提示する証明書の対象に含まれるホスト名を、メール基盤の接続先として定める。認証基盤は HTTPS と LDAPS に同一の証明書を用いるため、専用の名前を別に立てられない
  - VPS 側で当該ホスト名を tailnet 上のアドレスへ解決させる。名前は公開ドメインのものを用い、解決先のみを tailnet に向ける
  - 証明書の連鎖について、認証局と末端の証明書が分かれていることを確認する。認証局の証明書をそのまま末端として提示する構成は認証基盤に拒否される
  - VPS から当該ホスト名への LDAPS 接続が、証明書の検証を有効にしたまま成立する。認証局が発行した証明書、クラスタ上で稼働する認証基盤、および tailnet を経由する経路の 3 条件を同時に満たした状態で確認する
  - 当該通信が tailnet 上に閉じていることを確認する
  - _Requirements: 3.5, 3.6, 3.7, 1.8_
  - _Boundary: LdapExposure_
  - _Depends: 4.1_

- [ ] 5. メールボックスの格納と取得を構築する

- [x] 5.1 永続ボリュームと格納コンポーネントを定義する
  - メールボックスの実体を保持する永続ボリュームと、それを直接扱う格納コンポーネントを k3s 側の定義として作る。ネットワークファイルシステムを介さない
  - メールボックスの形式を、各メッセージが個別のファイルとなり操作が不可分であるものとする
  - 書き込み側を単一に保つ。複数の複製による同時アクセスを行わない。索引の写像とロックの方式にネットワークファイルシステム向けの調整を要しないことを、この構成の帰結として確認する
  - 永続ボリュームの定義に、同期による削除の対象から除外する注釈を与える。注釈は永続ボリュームの定義と同一の適用で与える。同期は削除を伴う設定で運用されるため、注釈を欠いた状態で定義が一時的に外れると蓄積したメールが失われる
  - 定義を GitOps の同期対象に置き、同期が成立して格納コンポーネントが稼働する
  - 注釈が付与された状態で、定義を一時的に外しても永続ボリュームが削除されないことを確認する
  - _Requirements: 5.1, 5.5, 5.7, 8.2_
  - _Boundary: MailboxBackend_
  - _Depends: 3.3_

- [x] 5.2 配送の受け口と取得の終端を構成する
  - 配送規約の受け口と取得の終端を、tailnet からのみ到達可能な形で公開する
  - 取得の終端に用いる証明書を供給し、当該経路で TLS を終端する
  - tailnet 上の別ホストから配送規約と取得規約の双方に接続が成立する
  - _Requirements: 5.2, 5.3, 4.7_
  - _Boundary: MailboxBackend_
  - _Depends: 5.1, 4.2_

- [x] 5.3 認証と静的な識別子を構成する
  - 格納コンポーネントの認証を認証基盤に対して行う。bind DN の形式は VPS 側と共通とし、アプリケーション指定を含む形式のみで成立させる
  - 接続はクラスタ内で完結させ、広域網を経由しない
  - メールボックスの位置および所有者の識別子を、認証基盤から取得せず静的な値として設定する
  - 利用者ごとの割当量について方針を定めた設定を保持する
  - アプリケーションパスワードで取得が成立し、主クレデンシャルでは成立しないことを確認する
  - _Requirements: 2.4, 4.4, 4.6_
  - _Boundary: MailboxBackend_
  - _Depends: 5.2_

- [x] 5.4 (P) メールボックスの容量を確認できる状態にする
  - メールボックスが占める容量を確認する手段を構成に含める
  - 現在の使用量が取得できる
  - _Requirements: 5.6_
  - _Boundary: MailboxBackend_
  - _Depends: 5.1_

- [ ] 6. VPS 上のメールサーバを構築する

- [x] 6.1 対象版を固定しロールとして構成する
  - VPS 上のメールサーバの構成を Ansible ロールとして作る
  - 対象とする版を固定し、当該版が前提とする設定名に一致する構成を保持する。対象は実証を行った系列とし、可変でない参照で指定する
  - 適用前に必要な変数の充足を検査し、不足している場合は開始前に適用を中止する
  - メールの待受に用いるポートを、ホスト自身のネットワークフィルタで通過させる。`iac-hygiene-remediation` はメールの待受に関する既存の定義を削除し、許可ポートの集合を意図した値に一致させる検証を持つため、ここで明示的に追加しなければ閉じられる
  - VPS で終端するポートと、格納側へ経路透過で中継するポートを区別して定義する。受信と送信の待受を VPS で終端し、取得の待受を格納側へ中継する。用いないポートについては待受も中継定義も持たない
  - VPS 上で凍結されている既存の中継設定は旧メール基盤のものであり、終端と中継の向きが本構成と異なる。ロールの初回適用で当該設定が消えるが、復活させない
  - 受信、送信、および取得の公開点を提供する状態でコンテナが稼働する
  - _Requirements: 4.1, 4.5, 4.11, 4.12, 8.1, 8.6_
  - _Boundary: EdgeMailServer_
  - _Depends: 5.3, 2.2_

- [x] 6.2 送信の認証を構成する
  - 認証を Dovecot の passdb によって行い、送信の認証も同一の passdb を経由させる
  - bind DN をテンプレートによって組み立てる方式で構成する。検索によって得た識別名で bind する方式を用いない。認証基盤が返す識別名にはアプリケーション指定が含まれないため、検索方式では資格情報の分離が成立しない
  - 認証に関する設定を環境変数ではなく設定ファイルの追加として与える。当該版では環境変数による指定が反映されない
  - 認証と利用者情報の項目定義を、既定の定義を差し替える形で与える。既定の定義は認証基盤に存在しない属性を参照しており、差し替えなければ認証が成立しない
  - 認証基盤の証明書を検証するために必要な認証局の証明書を、コンテナの信頼済み証明書の集合に配置する。配置しない場合、接続そのものが確立しない
  - 認証基盤への接続に LDAPS を用い、サーバ証明書を検証する。StartTLS を用いる設定と検証を無効化する設定を保持しない
  - 認証基盤への接続が確立できない場合、認証を成立させず失敗を記録に残す
  - 実行中の設定値を出力する操作で、追加設定と差し替えた項目定義の双方が反映されていることを確認する
  - アプリケーションパスワードで送信でき、主クレデンシャルでは送信できないことを確認する
  - _Requirements: 4.2, 4.3, 4.8, 4.9, 4.10, 2.4, 3.3, 3.4, 3.8_
  - _Boundary: EdgeMailServer_
  - _Depends: 6.1_

- [x] 6.3 宛先照合と配送先を構成する
  - 受信可能な宛先の照合を、検索用サービスアカウントの資格情報による認証基盤への検索として構成する。フィルタはメール属性とインデックス済み属性の論理積とする。宛先ごとの照合とドメイン単位の照合の双方を同じ形式で組み立てる
  - 照合を受理の前に行い、存在しない宛先を恒久的に拒否する。受理後に返送する経路を作らない
  - 受理したメールの配送先を、格納側の配送規約の受け口に向ける
  - 第三者による中継を許可しない
  - 格納側を停止させた状態で受信したメールが待ち行列に留まり、復旧後に配送されることを確認する
  - 認証を伴わない第三者宛の中継が拒否されることを確認する
  - _Requirements: 2.7, 5.4, 6.8_
  - _Boundary: EdgeMailServer_
  - _Depends: 6.2_

- [x] 6.4 証明書と取得の中継を構成する
  - メール用ホスト名の証明書を VPS 上に保持し、受信および送信の待受で用いる
  - 証明書の更新後、更新後の値が各待受に反映される状態にする。反映のために手動の操作を要しない
  - 取得の公開点を格納側へ経路透過で中継する。中継は内容を解さず、TLS の終端は格納側が行う
  - 中継の定義を既存の経路透過の仕組みに載せる。中継の対象は取得の待受のみとし、受信と送信の待受を中継しない
  - 外部から取得の公開点へ接続し、格納側のメールボックスが取得できる
  - 証明書を更新した状態で各待受へ接続し、更新後の証明書が提示されることを確認する
  - _Requirements: 4.7, 4.13_
  - _Boundary: EdgeMailServer_
  - _Depends: 6.3_

- [ ] 6.5 衛星サービスを有効化し動作を確認する
  - 迷惑メールの判定、認証の反復失敗に対する遮断、およびウイルスの検査を有効化する。いずれも既定では無効である。ウイルス検査はタスク 1.1 の実測結果が要求量を満たす場合にのみ有効化する
  - 迷惑メール判定機構が置き換える旧来の機構を無効化する。対象は DKIM 署名、認証結果の記録、送信者方針の検査、およびメッセージ検査の中継とし、いずれも既定で有効である。有効化する変数を足すだけでは無効にならない
  - DKIM 署名の担当を迷惑メール判定機構に一本化する。旧来の署名機構を有効なまま残すと署名が二重に付与され、受信側の検証に失敗する
  - 認証の反復失敗に対する遮断機構が要求するカーネル権限を、コンテナの定義に明示して与える。当該機構はホストのパケットフィルタを操作するため、既定の権限では有効化しても遮断が機能しない
  - 認証済みの送信に対して検査を適用するか否かを、明示的な宣言として保持する
  - 有効化と無効化を環境変数の宣言としてロールの定義に置き、当該定義を有効化状態の単一の情報源とする。コンテナ上での直接の変更を前提としない
  - 迷惑メールの判定を、判定を発火させる既知の検体を送信して確認する
  - ウイルスの検知を、検知を発火させる既知の検体を送信して確認する。有効化しない判断をした場合は当該確認を行わない
  - 反復失敗による遮断が発生することを、意図的な反復失敗によって確認する。あわせて遮断の解除手段を記述する
  - 送信メールに付与された署名が 1 つだけであることを確認する
  - _Requirements: 11.1, 11.2, 11.3, 11.4, 11.5, 11.7, 11.8, 11.9, 11.10_
  - _Boundary: EdgeMailServer_
  - _Depends: 6.4_

- [ ] 7. メールの到達性を確立する

- [ ] 7.1 送信元の識別に関する記録を定義する
  - MX の記録を公開する前に、メールボックスの保全が成立し書庫からの復元が確認済みであることを提示し、公開について承認を得る。MX の公開は外部からの受信を開始させ、受信したメールは再構築できない
  - 25 番ポートの遮断解除 (タスク 1.1) と MX の公開を、独立した 2 つの関門として扱う。前者は受信が成立しうるかを決め、後者は受信を開始させる。解除の完了は公開の承認を代替しない
  - 受信するドメインに対する MX の記録を定義する
  - 送信元を VPS に限定する送信者方針の記録を定義する。家庭回線からの送出が存在しないため、限定の範囲に家庭側のアドレスを含めない
  - 送信メールへの署名を有効にし、対応する公開鍵の記録を保持する。秘密鍵は記録に現れない
  - 認証に失敗したメールの扱いを指定する記録を定義する
  - 記録はすべて Terraform の定義として保持し、手動での作成を前提としない
  - 署名を有効にする前に公開鍵の記録を追加する。順序を逆にすると署名の検証が失敗する
  - 公開後、外部からの受信がメールボックスに現れることを確認する
  - _Requirements: 6.1, 6.2, 6.3, 6.4, 6.9, 6.10, 8.4_

- [ ] 8. 蓄積されるメールの保全を確立する

- [ ] 8.1 書庫の取り出しと保存先を構成する
  - 蓄積されるメールを復旧対象として扱う。受信したメールは再構築できないため、`iac-hygiene-remediation` がクラスタ上の永続データに適用する復旧対象外の扱いを適用しない
  - メールボックスを定期的に書庫として取り出し、複製する定期実行を構成する
  - 保存先を、メールボックスの実体を保持する物理ディスクとは異なる物理ディスク上に置く。この環境のディスクはいずれも単発構成で冗長性を持たないため、障害域の境界は物理ディスクである。ホストを分けるだけでは保全にならない
  - 分離が成立していることを、保存先とメールボックスの実体がそれぞれ載る物理ディスクを特定して確認する。メールボックスは k3s ノードの載る `sda` 上に、保全先は `sdc` 上にあり、分離は既に成立している
  - 分離によって残る障害の範囲を記録する。物理ディスク単体の故障では実体と成果物のいずれかが残るが、両者を収容するホストの全損では同時に失われる
  - メールボックスを保持する計算機を、`iac-hygiene-remediation` が構築する仮想化基盤の保護機構の対象一覧に含める。当該保護は粒度が粗いため第 2 の層とし、第 1 の層を書庫とする
  - 保存する世代数の上限を持たせる
  - 取り出しに失敗した場合、失敗を記録に残し成功したものとして扱わない
  - 書庫が生成され、世代数の上限を超えたものが削除される
  - _Requirements: 9.1, 9.2, 9.5, 9.6, 9.7, 9.8, 9.9, 9.10_
  - _Boundary: MailboxBackup_
  - _Depends: 6.5_

- [ ] 8.2 復元と再作成の手順を確立する
  - 書庫からメールボックスを復元する手順を記述する
  - 書庫から復元したメールボックスが取得できることを確認する。手順の記述だけでは確認としない
  - 署名の鍵および認証基盤上のメール用定義について、失われた場合の再作成手順を記述する。これらは復元ではなく再作成の対象である
  - 本タスクの完了が段階 4 の開始条件である。MX の公開以降に到着したメールは書庫からのみ復元できるため、復元の成立を確認するまで公開しない
  - _Requirements: 9.3, 9.4_
  - _Boundary: MailboxBackup_
  - _Depends: 8.1_

- [ ] 9. 利用者の設定手順を整える

- [ ] 9.1 (P) アプリケーションパスワードの発行手順を記述する
  - 発行の手順を記述したドキュメントを作る
  - 発行が命令行の操作のみで行えること、画面上の操作手段が存在しないこと、および対話的な端末を要するため自動化できないことを記述の冒頭に置く
  - 発行が利用者自身の認証済みセッションを要し、管理者が代理で発行できないことを記述する
  - 発行時に必要となる識別子の取得方法を記述する。発行の操作はアプリケーション定義の識別子を引数に取り、名称では指定できない
  - 発行されたパスワードが一度だけ表示され、再表示できないことを記述する
  - 有効期限を設定できないこと、および失効の手段を記述する。失効はメール利用者グループからの除外が最も速く反映される
  - 利用者のアカウント名がメールアドレスのローカル部と一致する必要があることを記述する
  - 記述に従って未経験の状態から発行が完了する
  - _Requirements: 10.1, 10.2, 10.3, 10.4, 10.6, 10.7, 2.13_
  - _Boundary: MailClientGuide_
  - _Depends: 6.4_
