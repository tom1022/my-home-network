# Implementation Plan

## 実行前の禁止事項

以下は全期間を通じて守る。タスクの完了後に確認するのではなく、着手前の制約として扱う。

- 認証基盤の利用者の所属を変更する作業を、本 spec の作業と並行して実行しない (要件 4.3)
- Proxmox の VM 105 および当該ゲストが占有するデバイスに対して、読み取りを含むいかなる操作も行わない (要件 4.4)
- 永続データを失う操作の前に、対象と影響範囲を提示して承認を得る (要件 4.5)
- 既存の到達手段を停止しない。旧環境のホストは本 spec の全期間を通じて稼働したままとする (要件 4.1, 4.2)

## 1. 前提の確定と旧環境の読み取り

- [x] 1.1 物理作業の提示と実施の依頼
  - ラズベリーパイの用意、microSD を boot 区画・USB 接続ドライブを root とする OS の導入、`cmdline.txt` の `root=PARTUUID=` 指定を、運用者が実施する作業として内容を提示する
  - 充てるドライブの SMART を確認する手順を含める。唯一の正を載せる前提のため
  - **sshd による鍵認証を有効にする。Tailscale SSH は有効にしない。**構成管理が用いる秘密鍵に対応する公開鍵を、運用者が `authorized_keys` へ手で置く
  - **タグを事前付与した認証キーで tailnet へ参加させる。**後からタグを張り替えると所有者と ACL の適用先が変わり、その時点で到達を失う
  - SD の boot 区画のみで起動できること (OTP の書き込みを要さないこと) を実機の起動で確認する
  - 旧環境の記憶装置を、新しい構成の成立を確認するまで保持する取り決めを記録する
  - 完了時、実施した作業の一覧が記録され、作業機から手動の SSH で鍵認証で入れる
  - _Requirements: 2.8, 4.6_

- [x] 1.2 公開対象と監視対象の到達可否の実測
  - **旧環境のホストから実測する。**Console セグメントに足を持つ既存のホストへ tailnet 経由で入り、そこから測る。新しい足の構築を待たない
  - DNS フィルタの管理画面はルータと同じ機体の 3000 番、ルータの SSH は 2222 番で待ち受けている。**それぞれをアドレスで指定して到達できることを確認し、宣言に入れる値として確定する**
  - **転送先をホスト名で宣言しない。**DNS フィルタの管理画面を名前で引くと、その機構が壊れたときに直すための画面へ到達できなくなる
  - 公開の対象と監視の対象のそれぞれへ到達できるかを実測する。対象は Console セグメント内の管理画面と、セグメント外の仮想化基盤の 2 ノード・クラスタの各ノード・ファイル共有・退避基盤・VPS
  - 到達できない対象は、監視の一覧から外すか、境界に必要な設定の内容を記録する。**境界の設定そのものは本 spec の対象外であり、記録に留める**
  - 完了時、宣言に埋める値が全て確定し、対象ごとの到達可否が一覧として残る
  - _Requirements: 2.3_

- [x] 1.3 旧環境の機能の棚卸しと再現要否の決定
  - 旧環境で稼働している機能を列挙し、代替するもの・同型で引き継ぐもの・再現しないものに分ける
  - 再現しないと決めたものについて、その理由を記録する
  - 保護されない形で置かれている秘匿値を特定し、新しい構成でどう保護するか、交換を要するかを決める
  - 本 spec では移設せず旧環境に残す資産を明示し、引き継ぎ先の決定が後続の spec に属することを記す
  - 完了時、再現を要する構成の一覧が確定し、2 章以降の宣言に落とす対象が漏れなく決まっている
  - _Requirements: 2.3, 2.4, 2.6_

- [x] 1.4 インベントリへの登録と適用のエントリポイントの新設
  - `console-pi` を接続対象のグループと、新設する Console 用のグループに追加する
  - 権限の昇格に必要なパスワードを、既存の VPS と同じ形で供給する
  - 既存の公開鍵配布の仕組みを適用する
  - **Console 用の適用のエントリポイントを新設する。**この時点では公開鍵配布のみを含む最小の内容とする
  - **`console-pi` が到達不能でも既存ホストへの適用が完走するようにする。**既知ホスト鍵の更新は接続対象のグループを総なめし、鍵の取得に失敗すると play ごと落ちる。全ての playbook がこれを冒頭で import しているため、この手当てが無いと新しいホストの停止が既存 9 ホストの適用を止める
  - 完了時、新設したエントリポイントを 2 回続けて適用しても 2 回目で変更が生じず、かつ `console-pi` を停止した状態で既存ホストへの適用が完走する
  - _Requirements: 2.1, 2.2, 2.7_

- [x] 1.5 秘匿値の供給経路の整備
  - Console の足で必要になる秘匿値を、一般名の変数から環境変数を参照する既存の間接化層に束縛する
  - 対象は権限昇格のパスワード、リバースプロキシの基本認証の資格情報、トンネルの token、ルータの API の資格情報、tailnet のタグ付き認証キー、**端末から対象へ接続するための秘密鍵**
  - 追加する変数名を該当する名前一覧のファイルに列挙する。あわせて、既存の通知先の変数がどの一覧にも記載されていない不整合を是正する
  - 完了時、宣言に平文の秘匿値が 1 つも含まれず、供給機構経由で全ての変数が解決する
  - _Requirements: 2.5_

## 2. tailnet への参加

- [x] 2.1 tailnet 参加のロールの新規作成と適用
  - **既存ロールからの抽出ではなく新規に作る。**既存の VPS 向けロールが持つのは tailscaled の設定ファイルのテンプレートとハンドラのみで、パッケージの導入・参加・タグの付与はいずれも存在しない
  - パッケージの導入、タグ付き認証キーでの参加、鍵の期限が無効化された状態の確認を含める
  - **Tailscale SSH を有効にしない。タグを SSH の認証に用いない。**既存 9 ホストと同じ鍵による認証に揃える
  - セグメント全体を広告しない。経路の広告を持たない状態にする
  - 完了時、`console-pi` が広告している経路を持たず、鍵の期限が無効で、通常の sshd で鍵認証の接続が成立する
  - _Requirements: 1.2, 1.11, 4.7_

- [x] 2.2 既存の VPS の tailnet 設定を新しいロールへ委譲
  - 既存の VPS 向けロールの tailscaled の設定を、新しいロールへ委ねる形に変える
  - **待受ポートの値は設定ファイルとファイアウォールの許可集合の両方が参照している。**唯一の保持者をどちらにするかを先に決め、両ロールが同じ変数を読む形にする
  - 再起動後に tailnet 経由の接続の復帰を待つ挙動を保持する
  - **単独で実行でき、単独で戻せる状態にする。**3 章以降の作業と混ぜない
  - 完了時、VPS への tailnet 経由の接続が従来どおり成立し、待受ポートが塞がっておらず、同じ責務のロールが 2 つ並存していない
  - _Requirements: 1.11_
  - _Depends: 2.1_

- [x] 2.3 到達手段の期限の棚卸し
  - 本 spec が新設する到達手段が持つ期限を全て列挙する。tailnet のノード鍵、トンネルの token、認証のセッション、外部公開のホスト名の証明書、基本認証の資格情報
  - それぞれについて、恒久化したものと、期限切れの前に更新するために監視で捕捉するものに分類する
  - 完了時、期限を持つ要素の一覧と、各要素の扱いが記録として残る
  - _Requirements: 4.7_

## 3. 到達手段

- [x] 3.1 公開対象の宣言とリバースプロキシの構築
  - 公開対象を、対象ごとの受け口のポート・tailnet のサービス名・外部公開時のホスト名・転送先・理由を持つ一覧として宣言する
  - **公開対象には、Console セグメントの管理画面に加えて、外形の状態一覧の画面と各ホストの資源の画面を含める。**いずれも loopback の待受を転送先とする
  - リバースプロキシは対象ごとに独立した受け口を持ち、要求元のホスト名を判定に用いない
  - 受け口を loopback に限定する。外部のインタフェースに開かない
  - 基本認証を掛ける。資格情報は供給機構から与える
  - 完了時、宣言した対象のみが応答し、待受の一覧に loopback 以外の待受が現れない
  - _Requirements: 1.1, 1.3, 1.4, 1.5_
  - _Depends: 1.2, 1.5_

- [x] 3.2 ホストの許可集合の適用
  - Console の足へ開放する経路を列挙し、専用の連鎖として構成する
  - **列挙とは別に、ループバックからの入力・確立済みおよび関連する接続・tailnet のインタフェースからの入力の 3 本を必ず含める。**これらを欠いた連鎖を差し替えると、適用したその接続ごと落ちる
  - 差し替えの順序を「連鎖を作る → 必須の 3 本が含まれることを検査する → 既定の連鎖へ挿す」に固定する。検査を通らない連鎖を挿さない
  - 完了時、差し替えの後に新しい接続が張れ、`console-pi` 自身の待受が宣言した列挙と一致する
  - _Requirements: 1.7_
  - _Depends: 3.1_

- [x] 3.3 ブラウザからの端末の提供
  - 宣言した宛先ごとに端末のプロセスを 1 つ用意する。宛先は名前・受け口のポート・接続先・理由を持つ一覧から生成する
  - **端末から対象へ接続するための資格情報を、宣言と供給機構から配備する。**対象側への公開鍵の登録が手作業になる場合はその内容を記録する
  - 既定が読み取り専用のため、入力を受け付ける設定を明示する。別の出自からの接続を拒否する検査を有効にする
  - 受け口を loopback に限定し、認証はリバースプロキシに一任する。資格情報をプロセスの引数に載せない
  - 完了時、認証を経た要求から端末が開いて入力が通り、プロセスの一覧に資格情報が現れない
  - _Requirements: 1.9, 2.5, 2.6_
  - _Depends: 3.1_

- [x] 3.4 単一の起点となる画面の配置
  - 常駐プロセスを持たない静的な配布物を配置し、リバースプロキシから配信する
  - リンクの一覧を、公開対象の宣言と端末の宣言から生成する。二重管理しない
  - 経路によって到達先の URL が異なるため、1 枚の画面に経路ごとのまとまりを置く
  - 完了時、この 1 枚から公開している全ての画面と全ての端末へ辿れる
  - _Requirements: 1.9_
  - _Depends: 3.1, 3.3_

- [x] 3.5 tailnet 経路の公開
  - 公開対象の宣言と端末の宣言の各エントリについて、tailnet のサービスを 1 つ用意し、対象ごとの受け口へ向ける適用を、tailnet 参加のロールの責務として実装する
  - パスの付加も非標準のポートも用いない。URL にポートもパスも現れない形にする
  - 用意するサービスの数が上限に収まることを確認する
  - 完了時、作業機に Tailscale のクライアント以外の設定を加えずに、全ての対象へ到達できる
  - _Requirements: 1.2, 1.8, 1.10_
  - _Depends: 2.1, 3.1_

- [ ] 3.6 tailnet 経路の到達性の検証
  - 公開対象の全てと端末の全てへ、端から端まで到達する
  - 起点の 1 枚から全ての対象へ辿れ、経路を切り替えても同じ対象へ到達でき、その際にクライアントの設定変更を要さないことを確認する
  - 非対話のクライアントから、人手の画面操作を経ずに接続と要求の双方が通ることを確認する
  - 宣言に無い宛先への要求が拒否されることを確認する
  - `console-pi` 自身の許可集合が、宣言した列挙と一致することを実測する。**境界側の到達制御は本 spec の対象外であり、必要な内容は記録に留める**
  - 転送先の画面が崩れずに表示されることを確認する
  - **リバースプロキシを停止した状態で、それを経由しない接続が成立することを実測する。**これが到達手段を失ったときの復旧経路である
  - 完了時、上記の全てが実測の記録として残る
  - _Requirements: 1.3, 1.6, 1.7, 1.8, 1.9, 1.10, 1.11_
  - _Depends: 3.2, 3.4, 3.5_

- [x] 3.7 外部からの経路の追加
  - 新しいトンネルを作成する。既存のトンネルは破棄も置換もしない
  - トンネルの経路の定義を、公開対象の宣言と端末の宣言の各エントリから生成する。末尾に受け皿を置く
  - 設定の保持先を片方に定め、排他となる指定を同時に行わない
  - 認証は既存の識別提供者をそのまま参照する。識別提供者を変更しない
  - トンネルの token を、権限を絞った環境変数のファイルから供給する。プロセスの引数に埋め込まない
  - 完了時、変更計画の出力に既存のトンネルと既存の名前解決の削除も置換も現れず、プロセスの一覧と履歴に token が現れない
  - _Requirements: 1.1, 1.6, 2.6_
  - _Depends: 3.1_

- [ ] 3.8 外部経路の到達性の検証
  - 既存の識別提供者の認証を経て、公開対象の全てと端末の全てへ到達する
  - 転送先の画面が崩れずに表示されることを確認する
  - **この経路が確立しない場合は、tailnet 経路のみの状態で運用を継続できる。**その判断をここで行う
  - 完了時、外部の経路からの到達の可否が実測の記録として残る
  - _Requirements: 1.1, 1.6_
  - _Depends: 3.6, 3.7_

## 4. 監視と通知

- [ ] 4.1 資源と記憶装置の監視の受けの配置と公開
  - 受けの機構を `console-pi` に配置し、待受を loopback に限定する。外部のインタフェースに開かない
  - 初回起動時の環境変数から管理利用者を自動で作る。**画面での初期設定を手作業として残さない**
  - 監視の対象とするホストを宣言として保持する。**宣言に無いホストは起動時に削除されるため、宣言がそのまま唯一の正になる**
  - **ホストに付ける名前に個人を識別する語を含めない。**通知の本文はこの名前を含み、文面を差し替える手段が無い
  - 管理利用者の資格情報、agent の自己登録に用いる token、通知の宛先を、環境変数を参照する既存の間接化層に束縛し、権限を絞った環境変数のファイルから供給する。プロセスの引数に載せない
  - 公開対象の宣言に 1 エントリとして加え、リバースプロキシ経由で両経路から到達させる
  - 完了時、各ホストの資源の画面が両経路から表示され、待受の一覧に loopback 以外が現れず、プロセスの一覧に秘匿値が現れない
  - _Requirements: 3.4, 3.5, 3.10, 3.14_
  - _Depends: 1.5, 3.1_

- [ ] 4.2 資源と記憶装置の計測の各ホストへの配布
  - 計測の agent を対象ホストへ配布し、token による自己登録で受けの一覧に載せる
  - 待受を受けから到達できる 1 つのアドレスに絞る。全インタフェースに開かない
  - **待受のアドレスを経路に合わせて選び、どのホストでも許可集合を変更せずに済ませる。**LAN 上のホストはそのホストの LAN のアドレス、VPS は tailnet のアドレスで待ち受ける。**VPS の許可集合は tailnet のインタフェースからの入力を無条件に通しており、tailnet 側で待ち受ける限り触らずに到達できる。**到達を司る許可集合に手を入れない
  - 記憶装置の状態と記憶領域の health の収集を、その実体を持つホストで有効にする。**`zfs-pool` の実体を持つのは `hp-z440` であり、その上で動く退避基盤のコンテナからはプールも記憶装置の状態も読めない**
  - 対象デバイスから記憶装置の属性が実際に読めることを、ホストごとに実測する
  - **VPS への適用は、tailnet の設定を触る作業と同時に行わない**
  - 完了時、宣言したホストが受けの一覧に現れ、資源・記憶装置・記憶領域の値が画面に出て、待受が指定したアドレス以外に無い
  - _Requirements: 3.7, 3.11, 3.12, 3.15_
  - _Depends: 4.1_

- [ ] 4.3 資源のアラートの宣言と適用
  - アラートを、閾値・継続分数・対象のホストを持つ一覧として宣言する
  - **設定ファイルにアラートを持てないため、適用は受けの REST API への要求で行う。**宣言から消えたアラートを残さない
  - 記憶装置の不良の兆候と記憶領域の劣化は常時有効の自動のアラートが担う。閾値を持たないため、何が通知され何が通知されないかが読み取れる形で宣言に併記する
  - **コンテナの健全性のアラートを設定しない。**このアラートだけが通知の本文にコンテナのログ抜粋を最大 1800 文字埋め込み、その内容を制御する手段が無い
  - 完了時、宣言したアラートのみが存在し、適用を 2 回続けても 2 回目で変更が生じず、コンテナの健全性のアラートが 1 つも設定されていない
  - _Requirements: 3.1, 3.5, 3.10, 3.11, 3.12_
  - _Depends: 4.2_

- [ ] 4.4 外形の死活監視と状態一覧の画面の構築
  - 外形の監視の機構を配置し、監視対象を宣言から生成する。宣言がそのまま監視対象事象の一覧を兼ねる
  - 履歴を永続化しない設定にする。蓄積のための資源を割かない
  - 対象は、到達可否の実測で到達できたものに限る。到達できない対象を一覧に入れない
  - **計測の agent を導入するホストを死活監視の対象から外す。**同じ停止で 2 通の通知が飛ぶ。ホストの到達不能の担い手は agent の有無で一意に決まる
  - **agent を導入しない対象と、資源の監視の受け自身の待受を対象に含める。**受けの停止を、受けから独立した位置で検知する。受けの外形は loopback の待受に対して見る。リバースプロキシを経由すると、リバースプロキシの停止と受けの停止が区別できない
  - 名前解決が単一の手作業の設定に依存している箇所を監視対象に含める
  - 受け口を loopback に限定し、公開はリバースプロキシを通す
  - 完了時、状態を一望する画面が表示され、各エントリから通知の要否が読み取れ、死活の対象と agent を導入するホストが 1 件も重複していない
  - _Requirements: 3.4, 3.5, 3.6, 3.13, 3.15, 3.17_
  - _Depends: 1.2, 3.1, 4.1_

- [ ] 4.5 通知の接続
  - 3 つの機構からの通知を、既存の通知と同じ宛先へ送る。**この宛先が要件 3.2 に適合することは設計で判断済みであり、実装時に再検討しない**
  - 外形の監視は汎用の webhook から、資源の監視は自身の送出機構から、同じ宛先へ直送する
  - 本文に含める要素を対象名と状態のみに限る。応答の本文や接続先の詳細が混入する経路を作らない
  - **資源の監視の本文は文面を差し替える手段を持たない。**含まれるのはホスト名・計測項目・値・閾値・継続分数と画面へのリンクであり、適合はホストに付ける名前だけで担保する
  - 状態が遷移したときにのみ発行し、継続中の異常を繰り返し送らない
  - 外形の監視の機構自身の停止を、そのユニットの失敗の通知で捕捉する
  - 完了時、通知の経路が 1 つに集約され、状態の遷移時にのみ発行されることを実測で確認できる
  - _Requirements: 3.1, 3.2, 3.10_
  - _Depends: 4.3, 4.4_

- [ ] 4.6 既製の機構が備えない検査の実装と Console の足への適用
  - 周期的に行う検査を次の 9 件とする。証明書の残存期間 (外部公開のホスト名を含む)、inode の使用率、時刻同期のずれ、ルートファイルシステムの読み取り専用への転落、OOM killer の発動、swap の使用率、ラズベリーパイの給電不足と周波数の抑制のフラグ、fail2ban の jail が空でないことと特定のアドレスの ban、記憶領域の整合検査のエラーと最終実行からの経過日数
  - **記憶領域の使用率と負荷を検査に含めない。**資源の監視の機構が担う
  - 時系列を保持しない。都度取得して閾値を判定するのみとする
  - 通知を自前で送らず、失敗の状態にすることだけを行い、通知は既存の仕組みに委ねる
  - 標準出力に測定値を出さない
  - **前回値との比較を要するのは OOM killer の検知のみ。**状態のファイルを 1 つ持ち、失われた場合は現在値を基準に取り直す
  - まず `console-pi` にのみ適用する
  - 完了時、閾値を超えた対象について通知が届き、出力に測定値が現れず、上記の 9 件に無い検査がスクリプトに含まれていない
  - _Requirements: 3.1, 3.10, 3.12, 3.13, 3.15, 3.16_
  - _Depends: 4.5_

- [ ] 4.7 監視と通知の他ホストへの展開
  - 既存の通知の仕組みは現在 1 つの playbook の対象にしか導入されていない。残るホストへ導入する
  - 権限の昇格に必要な値が用意されていないホストについて、供給経路を整える
  - 検査を、仮想化基盤の 2 ノード、クラスタの各ノード、ファイル共有、退避基盤、VPS へ展開する。**適用先が 1 ホストに限られる検査がある。**給電のフラグは `console-pi`、fail2ban は VPS、記憶領域の整合検査は `hp-z440` のみを対象とする
  - 検査と計測の agent を同一のエントリポイントで適用する
  - **VPS への適用は、tailnet の設定を触る作業と同時に行わない**
  - 完了時、対象の全ホストで検査のタイマーが稼働し、適用を 2 回続けても 2 回目で変更が生じない
  - _Requirements: 3.1, 3.9, 3.10_
  - _Depends: 4.2, 4.6_

- [ ] 4.8 常駐と保持量の実測
  - 全ての常駐が揃った状態で `console-pi` のメモリの使用量と平常時の負荷を実測して記録する。**上限値は設計で固定していない。実測値をもって判断する**
  - **メモリ 1GB の機体に資源の監視の受けの常駐が加わる。**この機体でこの機構を動かした報告が存在しないため、実測が唯一の判断材料になる
  - 閲覧のために保持している計測値の実際の量を実測して記録する
  - 退避基盤のコンテナの agent が報告する資源の値が、コンテナのものかホストのものかを実測する。ホストのものであれば、その項目を当該ホストの対象から外す
  - **実測値が機体の容量に対して過大であった場合の最初の調整点は、端末の常駐数を減らすことである**
  - 完了時、常駐の総量と保持している計測値の量が記録として残り、機体の容量に見合うかの判断が根拠とともに記録されている
  - _Requirements: 3.4, 3.7_
  - _Depends: 4.7_

- [ ] 4.9 通知の到達と本文の確認
  - 外形の監視の対象を意図的に落とし、通知が届くことを確認する
  - 閾値を一時的に下げ、既製の機構が備えない検査と資源の監視の双方から通知が届くことを確認する
  - 資源の監視の受けを停止し、外形の監視から通知が届くことを確認する
  - 計測の agent を停止し、受けから到達不能の通知が届くことを確認する。**同じホストについて外形の監視からも通知が届く場合は、監視対象の分担が守られていない**
  - 通知の宛先を誤った値にして、不達が成功と区別されることを確認する
  - **届いた通知の本文を実物で確認し、秘匿値・応答の本文・接続先の詳細・運用者個人を識別する情報が含まれないことを記録する**
  - 完了時、定義の存在ではなく実際の到達と本文の中身をもって確認できた記録が残る
  - _Requirements: 3.3, 3.10, 3.17_
  - _Depends: 4.7_

- [ ] 4.10 既存の収集の機構の存廃の判断の記録
  - 旧環境で稼働している収集の機構と可視化の機構について、維持と廃止のどちらを採るかを決定し、判断の根拠とともに記録する
  - 収集していた対象ごとに、外形の死活・資源と記憶装置の監視・既製の機構が備えない検査の 3 者のどれで代替されるかを対応づける
  - 実際の停止と、停止に先立つ対象ごとの通知の要否の判断は後続の spec が担うことを明記する
  - 完了時、廃止の決定と代替の対応づけが記録として残る
  - _Requirements: 3.8_
  - _Depends: 4.4_

## 5. 遠隔起動

- [ ] 5.1 送出の前提の確認と検証対象の決定
  - 送出を担う機器への追加の機能の導入を、運用者が実施する作業として内容を提示する
  - 対象の機器が遠隔起動に対応しているかを確認し、対応していないものを理由とともに記録する
  - 対象側で設定が再起動をまたいで保持されるようにする
  - **電源断を伴う検証に使える対象を特定する。**稼働中の仮想化基盤のノードを落とすと、その上の全てのゲストが停止する。影響範囲を提示して承認を得る
  - **経路上でブロードキャストの転送を有効化しない。**送出は対象と同じ範囲に足を持つ機器に委ねる
  - 完了時、対応する対象と対応しない対象が理由つきで一覧になり、検証に使う対象と承認の記録が残る
  - _Requirements: 4.5, 4.6, 5.5_

- [ ] 5.2 遠隔起動の対象の宣言と要求の発行
  - 起動の対象を、名前・物理アドレス・送出元のインタフェース・理由を持つ一覧として宣言する
  - 送出そのものは行わず、対象と同じブロードキャストの範囲に足を持つ機器の API へ要求を発行する
  - 送出先の機器に対象を登録しない形式を用いる。一覧の唯一の保持者は本リポジトリとする
  - 認証は供給機構から与える資格情報で行う
  - 完了時、別のセグメントにある対象が起動し、資格情報を外した要求が拒否され、対象の再起動後も設定が保持されている
  - _Requirements: 5.1, 5.2, 5.3, 5.4_
  - _Depends: 1.5, 5.1_

- [ ] 5.3 起動の失敗の判別の確認
  - 起動の要求の後に、死活監視が対象の状態を判定することを確認する
  - 起動しない対象について、異常が報告され続けることを確認する
  - 完了時、起動が成立しなかったことを人手の確認なしに判別できる
  - _Requirements: 5.6_
  - _Depends: 4.4, 5.2_

## 6. 統合と完走の確認

- [ ] 6.1 起動区画の読み取り専用への切り替え
  - boot 区画を読み取り専用で保持し、カーネルとファームウェアの更新の前後でのみ書き込みを許す手順を宣言に含める
  - **パッケージの導入が全て終わった後に切り替える。**先に切り替えると、以後の導入が更新を巻き込んだ時点で失敗し、パッケージ管理が壊れた状態で残る
  - 完了時、切り替えの後に適用を 2 回続けても 2 回目で変更が生じず、更新の手順が実際に通る
  - _Requirements: 2.7_
  - _Depends: 3.8, 4.9, 5.3_

- [ ] 6.2 宣言の不変条件の検査と日常の適用への組み込み
  - 宣言の一覧が持つ不変条件を適用時に検査する。受け口のポートとサービス名の一意性、理由を持たないエントリの不在、死活監視の対象と計測の agent を導入するホストが重複しないこと
  - Console の足への適用と、検査および計測の適用を、日常の適用のエントリポイントに組み込む。**挿入位置は既存の適用が全て終わった後とする**
  - **Console 関連の秘匿値が未設定でも、既存ホストへの適用が完走することを確認する**
  - 静的な検査が CI で通ることを確認する
  - 完了時、不変条件の違反が適用時に検出され、日常の適用が既存ホストと新しいホストの双方で完走する
  - _Requirements: 2.7_
  - _Depends: 6.1_

- [ ] 6.3 完走の確認と記録の整合
  - 旧環境の機能の一覧について、1 章で決めた再現要否と、実際に再現したものが一致することを確認する。差分があれば理由を記録する
  - 保護されない形で置かれていた秘匿値について、新しい構成で保護された形になったこと、および交換の要否の判断を記録する
  - 旧環境の記憶装置が現存し、消去も再利用もされていないことを確認する
  - 実行前の禁止事項の各項目について、違反が無かったことを判定する
  - 到達手段を失ったときの物理的な復旧の手順を記録する
  - 完了時、上記の各項目が違反なし・差分なしと判定され、判定の根拠が記録として残る
  - _Requirements: 2.4, 2.6, 2.8, 4.1, 4.2, 4.3, 4.4, 4.5_
  - _Depends: 6.2_
