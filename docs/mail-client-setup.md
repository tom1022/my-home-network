# メールクライアント設定ガイド

メール基盤 (`mail.fickledev.com`) を利用するために、アプリケーションパスワードを発行し、
メールクライアントに接続設定を行う手順を示す。

対象読者は、Kanidm 上に利用者アカウントを持ち (アカウント名がメールアドレスのローカル部と
一致しており)、当該アカウントに主資格情報 (パスワードおよび TOTP) が設定済みで、
`mail_users` グループに所属している利用者である。アカウントの新規作成・グループへの追加は
管理者が別途行う。

## 1. アプリケーションパスワードの発行

メールクライアントに設定する資格情報は、ログインや sudo に用いる主資格情報とは別系統の
「アプリケーションパスワード」である。発行には以下の制約がある。

- **発行は命令行 (`kanidm` CLI) の操作のみで行える。画面上 (Web UI) に発行の操作手段は存在しない。**
- **発行は対話的な端末を要する。** ログインと再認証がパスワード・TOTP コードの対話入力を要求するため、
  スクリプトによる自動化はできない。
- **発行には利用者自身の認証済みセッションが必要である。管理者が本人に代わって発行することはできない
  (代理発行は認証基盤に拒否される)。**
- 発行の操作はアプリケーション定義の **UUID** を引数に取る。`mail` のような名称では指定できない。
  UUID は手順中で取得する。

### 事前準備

- `kanidm` CLI (Kanidm サーバと同じ 1.11.x 系列)。ローカルにインストール済みでなければ、
  以下のように Docker イメージで代替できる。

  ```sh
  alias kanidm='docker run --rm -it kanidm/tools:1.11.1 kanidm'
  ```

- 以下の手順では `<アカウント名>` を自分の Kanidm アカウント名 (メールアドレスのローカル部) に、
  `<接続先>` を `https://kanidm.fickledev.com` に読み替える。

### 手順

1. ログインする。パスワード、続けて TOTP コードの入力を求められる。

   ```sh
   kanidm login -D <アカウント名> -H <接続先>
   ```

2. メール用アプリケーション定義の UUID を取得する。

   ```sh
   kanidm system application get mail -D <アカウント名> -H <接続先>
   ```

   出力の `id` フィールドが UUID である。

   ```json
   {
     "id": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
     "name": "mail",
     "displayname": "Mail",
     ...
   }
   ```

3. 再認証する (特権操作のための短期間の昇格。パスワードと TOTP コードを再度求められる)。

   ```sh
   kanidm reauth -D <アカウント名> -H <接続先>
   ```

4. アプリケーションパスワードを発行する。`<UUID>` は手順 2 で取得した値、`<ラベル>` は
   端末やクライアントを識別するための任意の名前 (例: `iphone`, `thunderbird-desktop`)。

   ```sh
   kanidm person applications create <アカウント名> <UUID> "<ラベル>" -D <アカウント名> -H <接続先>
   ```

   出力例:

   ```text
   id:     xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
   label:  <ラベル>
   secret: xxxxx-xxxxx-xxxxx-xxxxx
   This secret will only be shown ONCE!
   ```

   **`secret` の値がアプリケーションパスワードであり、この画面にしか表示されない。
   再表示する手段は存在しないため、直後にメールクライアントへ設定するか、パスワード
   マネージャ等へ保管すること。** `id` は失効 (手順を後述) に使うので、あわせて控えておくと良い。

### 有効期限と失効

- アプリケーションパスワードに **有効期限は設定できない**。発行したパスワードは明示的に
  失効させるまで有効であり続ける。
- 個別の失効: 発行時に控えた `id` を使う。

  ```sh
  kanidm login -D <アカウント名> -H <接続先>
  kanidm reauth -D <アカウント名> -H <接続先>
  kanidm person applications delete <アカウント名> <id> -D <アカウント名> -H <接続先>
  ```

- **その利用者が発行した全てのアプリケーションパスワードを一括かつ最速で失効させたい場合は、
  `mail_users` グループから当該利用者を除外する。** 個別のパスワードを 1 件ずつ削除するより
  反映が速く、紛失した端末が複数ある場合や退会時の遮断に適する。グループからの除外は管理者が行う。

## 2. メールクライアントの接続設定

| 用途 | 接続先ホスト名 | ポート | 暗号化 | 認証方式 |
|---|---|---|---|---|
| 送信 (SMTP submission) | `mail.fickledev.com` | `587` | STARTTLS | パスワード認証 (SMTP AUTH) |
| 送信 (SMTP submission、代替) | `mail.fickledev.com` | `465` | Implicit TLS (SSL) | パスワード認証 (SMTP AUTH) |
| 受信 (IMAP) | `mail.fickledev.com` | `993` | Implicit TLS (SSL/IMAPS) | パスワード認証 (IMAP LOGIN) |

- **ユーザー名は、メールアドレスではなく Kanidm のアカウント名 (メールアドレスのローカル部) を、
  `@` 以降を含めずに設定する。** 例えば `mailguide9x@fickledev.com` 宛のメールを扱う場合、
  クライアントのユーザー名欄には `mailguide9x` とだけ入力する。
- パスワード欄には手順 1 で発行したアプリケーションパスワードを設定する。主資格情報 (ログイン用の
  パスワード) はメールクライアントには使用できない。
- 25 番ポート (SMTP, 受信専用) と 143 番ポート (平文 IMAP) はメールクライアントの設定には使わない。
  143 番と 4190 番 (Sieve) は待ち受けていない。

## 3. 動作確認の記録

以下は本ドキュメントの手順のみを実行して、発行から送受信までが成立することを確認した記録である
(検証用の使い捨てアカウントを用い、確認後に削除した)。

**1 節 (アプリケーションパスワードの発行)**: 上記の手順をそのまま実行し、
`kanidm login` → `kanidm system application get mail` (一般利用者権限で `id` を取得できることを
確認) → `kanidm reauth` → `kanidm person applications create` の順で、追加の知識を要さず
発行が完了することを確認した。発行された `secret` を用いた 2 節の接続確認も成立した。

失効についても、`kanidm person applications delete` の実行直後に同じアプリケーションパスワードでの
IMAP ログインが `AUTHENTICATIONFAILED` で拒否されることを確認した。

**2 節 (接続設定)**: Python の `smtplib` / `imaplib` を用い、1 節で発行したアプリケーションパスワードと
`mail.fickledev.com` への実接続で以下を確認した。

| 項目 | 結果 |
|---|---|
| 587 (STARTTLS) での SMTP AUTH と送信 | 成立 |
| 465 (Implicit TLS) での SMTP AUTH | 成立 |
| 993 (IMAPS) での IMAP LOGIN | 成立 |
| 587 で送信したメールを 993 経由の INBOX から取得 | 成立 (件名の一致を確認) |

いずれもユーザー名はアカウント名のローカル部のみ (`@` 以降を含めない) を用いている。
